# 바이브 코딩 5요소 채점 루브릭 v1.0

> 강의 "바이브 코딩이란?" (정금구) 부속 실습 앱용 채점 기준서
> R-PCCO 코딩 응용판 — 1차 강의 R-PCCO 루브릭을 코딩 맥락으로 재해석
> 최종 수정: 2026-05-12

---

## 0. 설계 철학

### 0.1 채점의 목적
수강생이 작성한 **코딩 묘사 프롬프트**(Claude Artifacts·Code에 던질 자연어)가 5요소 중 어디가 약한지 즉시 인지하고, **그 자리에서 Artifacts에 붙여넣으면 작동하는 완성형 프롬프트**를 돌려받는 것이 목표.

3차 강의(SSDHR)까지의 채점기는 "이렇게 보강하세요" 식의 일반 피드백이었으나, 바이브 코딩에선 **개선 예시(improved_example) 자체가 실행 가능한 산출물**이어야 한다. 강의 실습 흐름이 "채점 통과 → claude.ai 붙여넣기 → 미리보기에 앱 출현"이라서.

### 0.2 세 가지 원칙
1. **투명성** — 왜 이 점수를 받았는지 감지된 텍스트와 함께 근거 제시
2. **즉시 실행 가능성** — `improved_example`은 `claude.ai` 채팅창에 그대로 붙여넣으면 Artifacts에 작동하는 앱이 나오는 250~500자 완성형 프롬프트
3. **긍정성** — 잘한 점(strengths)을 먼저 짚은 뒤 개선점(improvements) 제안

### 0.3 4차 강의만의 고유 채점 축
이전 세 강의(R-PCCO, I-MRKO, SSDHR)와 가장 다른 점:
- **평가 대상은 코딩 묘사문** — 코드 품질이 아니라 "묘사의 구체성"을 평가
- **Where(디바이스)가 절대 빠지면 안 됨** — 코딩에서 디바이스 미명시는 결과를 산으로 보냄 (PC 기준 생성 → 핸드폰에서 깨짐)
- **출력에 파일 종류 명시 필수** — "한 페이지 HTML", "React 컴포넌트" 같은 결과물 종류가 핵심
- **Artifacts 호환성**이 가점 — 단일 파일 출력, 외부 라이브러리 의존 최소화 등

### 0.4 총점 체계
- 각 요소 **20점 × 5 = 100점 만점**
- 가점 최대 **+8점** (4개 항목 × +2~+3점, 단 총점 100점 초과 불가 — cap)
- 감점 최대 **-10점**
- 등급: **S**(95+) / **A**(85+) / **B**(70+) / **C**(50+) / **D**(30+) / **F**(30 미만)

### 0.5 R-PCCO·SSDHR 루브릭과의 관계
바이브 코딩 5요소는 **R-PCCO와 동일한 다섯 칸**이지만 평가 기준이 코딩 맥락으로 변형됨:
- R (역할): "10년차 마케터" → **"10년차 모바일 UI 디자이너"** (코딩 직군)
- P (목적): 행동 유도 → **앱 사용자 행동 유도** (클릭, 입력 등)
- C (맥락): Who·Where·Why → **Who·디바이스·When** (Where가 결정적)
- C (제약): 분량·톤·어휘·구조 → **디자인·분량·기술·금지** 4카테고리
- O (출력): 결과물 형식 → **파일 종류 + 섹션 구조** (HTML 한 파일 등)

## 1. R — Role (역할) · 20점

### 1.1 평가 관점
어떤 개발자·디자이너 시점에서 만드는지가 디자인 톤·UI 패턴을 결정.

### 1.2 점수 기준표

| 점수 | 레벨 | 기준 | 코딩 맥락 예시 |
|:---:|:---:|---|---|
| **0** | none | 역할 지정 없음 | "앱 만들어줘" |
| **5** | vague | "전문가", "AI", "너" 등 추상 지칭만 | "너는 전문가야" |
| **10** | basic | 직군만 | "너는 디자이너야" |
| **15** | good | 경력 + 직군 | "너는 10년차 디자이너야" |
| **20** | excellent | 경력 + 세부 분야 | "너는 10년차 모바일 UI 디자이너야" |

### 1.3 감점 요소
- **과장된 역할 (-2점)**: "세계 최고", "천재", "전설의" 등

### 1.4 피드백 템플릿
- `0~5점` → "역할이 없거나 모호해요. '너는 N년차 [세부 분야] 디자이너야'로 시작하세요."
- `10점` → "직군은 있어요. 경력(연차) + 세부 분야(예: '모바일 UI', '행정 UX', '게임 인터페이스') 추가."
- `15점` → "경력+직군 OK. 세부 분야 한 단어만 더 (예: 'UI', 'UX', '게임', '미니멀리스트')."

## 2. P — Purpose (목적) · 20점

### 2.1 평가 관점
같은 자기소개 페이지라도 채용용·SNS용·IR용·결혼정보용이 완전 다른 앱이 됨.

### 2.2 점수 기준표

| 점수 | 레벨 | 기준 | 예시 |
|:---:|:---:|---|---|
| **0** | none | 목적 없음 | "앱 만들어줘" |
| **5** | implicit | 결과물 종류만 | "자기소개 페이지" |
| **10** | basic | "~위해서" 명시 | "채용 지원용 자기소개 페이지" |
| **15** | specific | 대상의 구체적 행동 유도 | "면접관이 3분 안에 핵심 경력을 파악하도록" |
| **20** | measurable | 목적 + 측정/성공 기준 | "면접관이 5초 안에 직무 적합도를 파악하고 다음 단계로 넘기게 만들기" |

### 2.3 피드백 템플릿
- `5점` → "결과물 종류만 있어요. '채용 지원용', 'IR용' 같이 '~를 위해'를 한 줄 추가."
- `10점` → "용도는 있어요. 사용자(보는 사람)가 무엇을 하길 원하는지 명시 (예: '~ 클릭하도록', '~ 검토하도록')."

## 3. C₁ — Context (맥락) · 20점

### 3.1 평가 관점 — 3차원
- **Who** (누가 쓰나): 면접관·친구·60대 부모님·투자자 — 글자 크기, 톤, 정보량 결정
- **Where** (어떤 기기에서) — **★ 코딩에서 가장 중요한 변수**: 모바일·데스크탑·태블릿
- **When** (어떤 상황·시점): 출퇴근 5초 스캔·면접관 3분 검토·발표 60초 — 정보 밀도 결정

### 3.2 점수 기준표

| 점수 | 레벨 | 기준 | 예시 |
|:---:|:---:|---|---|
| **0** | none | 맥락 없음 | - |
| **5** | 1D | 3차원 중 1개 | "20대 대상" |
| **10** | 2D 또는 Where 없는 3D | 2차원만 OR Where 없는 3D | "20대 면접관, 점심 후" (디바이스 누락 → 캡) |
| **15** | 3D | 3차원 모두 + Where 포함 | "40대 채용 담당자, PC 브라우저, 3분 검토" |
| **20** | 3D+granular | 각 차원이 구체적 | "40대 IT 회사 채용 담당자, 1920×1080 PC 브라우저, 점심 후 3분 스캔" |

### 3.3 캡 규칙 — Where 없으면 10점 상한
디바이스(Where) 미명시 시 AI가 데스크탑 기준으로 생성 → 핸드폰에서 글자 깨짐·버튼 안 보임. 이 결함이 결과를 산으로 보내므로 점수에서 강하게 반영.

### 3.4 피드백 템플릿
- Where 누락 시 → "디바이스 한 줄 추가: 'PC 브라우저', '모바일 핸드폰', '태블릿' 중 하나."
- 1D만 있을 때 → "Who/Where/When 3차원 중 2개가 빠졌어요. 누가·어디서·언제 보는지 모두 명시."

## 4. C₂ — Constraints (제약) · 20점

### 4.1 평가 관점 — 4카테고리 (강의 슬라이드 13)
- **디자인**: 흰 배경·검정 회색 톤·둥근 모서리·파스텔
- **분량·크기**: 한 페이지·스크롤 한 화면·모바일 한 손 조작
- **기술**: HTML 한 파일·외부 라이브러리 없이·이미지 없이 텍스트만
- **금지**: 이모지·외부 이미지·자동 재생

### 4.2 점수 기준표

| 점수 | 레벨 | 기준 | 예시 |
|:---:|:---:|---|---|
| **0** | none | 제약 없음 | - |
| **5** | 1개 | 1카테고리 | "흰 배경" |
| **10** | 2개 | 2카테고리 | "흰 배경, 한 페이지" |
| **15** | 3개+구체 | 3카테고리 + 각각 구체 | "흰 배경 + 검정 회색 톤, 한 페이지 내, HTML+CSS만" |
| **20** | 4개 또는 3개 granular | 4카테고리 모두 OR 3개가 매우 구체 | "흰 배경, 한 페이지 모바일 한 손 조작, HTML+CSS 외부 라이브러리 X, 이모지 금지" |

### 4.3 감점 요소
- **모순 (-3점)**: 양립 불가 지시 (예: "복잡한 기능 / 한 화면에 다")
- **부정형 과다 (-2점)**: "~하지 마" 3회 이상

### 4.4 피드백 템플릿
- `5~10점` → "제약 2~3종 더 추가. 디자인 톤(흰 배경)·분량(한 페이지)·기술(HTML+CSS 외 X)·금지(이모지 X) 중 빠진 것 보강."
- 부정형 과다 시 → "'~하지 마'를 '이렇게 해줘' 긍정형으로 바꾸세요. 예: '이모지 쓰지 마' → '텍스트만 사용'."

## 5. O — Output (출력) · 20점

### 5.1 평가 관점
코딩의 출력 = **결과물 형태 + 파일 종류**. 안 정하면 AI가 텍스트 답변으로 fallback.

### 5.2 점수 기준표

| 점수 | 레벨 | 기준 | 예시 |
|:---:|:---:|---|---|
| **0** | none | 형식 지정 없음 | "앱 만들어줘" |
| **5** | type-only | 결과물 종류만 | "페이지 만들어줘" |
| **10** | type+basic | 파일 종류 일부 명시 | "HTML로 만들어줘" |
| **15** | type+detailed | 파일 종류 + 구조 일부 | "한 페이지 HTML, 상단 헤더 / 중간 본문 / 하단 푸터" |
| **20** | type+schema | 파일 종류 + 섹션·요소까지 구체 | "한 페이지 HTML 한 파일, 상단 이름·직함 / 중간 경력 3줄+강점 3개 / 하단 연락처" |

### 5.3 1주차 권장 출력
- **단일 페이지 HTML** 하나만 — Artifacts 미리보기 호환성 최고
- React 컴포넌트·인터랙티브 미니 앱·데이터 시각화 등은 4주차부터

### 5.4 피드백 템플릿
- `0~5점` → "'한 페이지 HTML로 만들어줘' 같은 파일 종류 명시 추가."
- `10점` → "파일 종류는 있어요. 어떤 섹션이 어디에 들어가는지 (헤더/본문/푸터) 한 줄 추가."

## 6. 가점 (bonuses) — 최대 +8점

각 가점은 적용 시 양수 points, 해당 없으면 `points: 0`로 기록.

| type | 점수 | 조건 |
|---|:---:|---|
| `device_specified` | +3 | 디바이스(모바일/PC/태블릿/특정 화면 크기) 명시 — **바이브 코딩 핵심** |
| `tech_stack_clear` | +2 | 사용/금지 기술 명시 (HTML 한 파일 / 외부 라이브러리 X / React 등) |
| `interaction_explicit` | +2 | 사용자 인터랙션(버튼 클릭·호버·입력) 구체 명시 |
| `single_file_output` | +2 | "한 페이지 HTML" 같은 단일 파일 출력 명시 (Artifacts 호환) |

가점 합계 8점 상한. 캡 적용 시 가장 가치 높은 것부터 우선 반영.

## 7. 감점 (penalties) — 최대 -10점

| type | 점수 | 예시 |
|---|:---:|---|
| `exaggerated_role` | -2 | "세계 최고", "천재 개발자", "전설의 디자이너" |
| `vague_intent` | -2 | "예쁘게", "감성 있게", "잘 만들어줘" |
| `negative_overuse` | -2 | "~하지 마" 3회 이상 |
| `contradiction` | -3 | 양립 불가 지시 ("복잡한 기능 / 한 화면에") |
| `scope_too_big` | -3 | "쇼핑몰 만들어줘" — Artifacts 단일 파일로 불가능한 스코프 |

감점 합계 10점 상한.

## 8. improved_example 작성 규칙 — ★ 가장 중요

이 필드는 사용자가 결과 화면에서 복사 버튼을 눌러 `claude.ai`에 붙여넣으면 **Artifacts로 즉시 작동하는 앱**을 받기 위한 것.

### 8.1 필수 포함 6항목
1. **역할 한 줄** (경력 + 세부 분야)
2. **목적 한 줄** ("~하기 위해" + 사용자 행동 유도)
3. **대상 + 디바이스 + 상황** (Who + Where + When) — Where(디바이스)는 절대 빠지면 안 됨
4. **디자인 톤·분량·기술 제약** (최소 3가지)
5. **사용자 인터랙션 묘사** (어떤 버튼/링크/입력이 있고 어떻게 동작하는지)
6. **출력 종결**: "한 페이지 HTML로 만들어줘" 또는 "Artifacts로 단일 HTML 파일로 만들어줘"

### 8.2 작성 규칙
- 사용자의 원래 의도·주제 그대로 유지
- 길이: **250~500자** (너무 짧으면 묘사 부족, 너무 길면 Artifacts가 헤맴)
- 외부 이미지·외부 폰트·외부 라이브러리 의존 피하라고 명시 (Artifacts는 인라인 자원만 안정)
- 마지막은 명령형 한 줄로 종결

### 8.3 예시 (사용자 입력 "자기소개 페이지 만들어줘"에 대한 improved_example)
> 너는 10년차 모바일 UI 디자이너야. 채용 지원용 한 페이지 자기소개를 만들어줘 — 40대 IT 회사 채용 담당자가 PC 브라우저에서 점심 후 3분 안에 직무 적합도를 파악하고 다음 단계로 넘길지 결정할 수 있도록. 디자인은 미니멀, 흰 배경에 검정·회색 톤, 둥근 모서리 8px, Pretendard 또는 system-ui 한글 폰트, 한 페이지에 다 들어가게 스크롤 최대 1.5화면. 외부 이미지·외부 폰트·외부 라이브러리 사용 금지(HTML+인라인 CSS만). 상단에는 이름·직함·한 줄 캐치프레이즈, 중간에는 핵심 경력 3줄과 강점 3개를 카드 형태로, 하단에는 이메일·포트폴리오 링크와 PDF 다운로드 버튼. 이메일 텍스트 클릭 시 `mailto:` 동작, 포트폴리오 링크는 `target=_blank`, PDF 다운로드 버튼은 alert로 'PDF 준비 중'을 띄움. 한 페이지 HTML 한 파일로 만들어줘.

위 텍스트는 그대로 `claude.ai/new`에 붙여넣으면 Artifacts에 작동하는 자기소개 페이지가 즉시 만들어진다.

### 예시 2 · A등급 (88점) — 강의 슬라이드 5 라이브 데모
**입력**
> 너는 모바일 앱 UI 디자이너야. 회식 자리에서 직장인들이 분위기 풀려고 핸드폰으로 잠깐 보는 앱을 만들거야. 사용자는 30~40대 직장인, 5초 안에 결과를 봐야 해. 버튼 하나 누르면 오늘의 회식운이 나오고, 다시뽑기 가능하게. 너무 진지하지 않고 살짝 유머 있게. 한 페이지 HTML로 만들어줘.

## 11. 구현 시 주의사항

- **응답 시간**: Sonnet 4.6 기준 3~5초. 로딩 애니메이션 + "AI가 5요소를 해부하는 중..." 문구로 대기 체감 감소
- **토큰 비용**: 입력 ~2200토큰 (시스템 프롬프트) + 출력 ~600토큰 ≈ **요청당 $0.003~0.004**
  - 30명 × 5회 실습 = 150회 = **약 $0.5**
- **JSON 파싱 실패 대비**: 재시도 1회 → 실패 시 사용자에게 에러 + 다시 시도 안내
- **악용 방지**:
  - 입력 1500자 제한
  - 사용자당 분당 10회 rate limit
- **DB 모드 'vibe'**: `sessions.mode IN ('prompt', 'instruction', 'image', 'vibe')` (v4 마이그레이션, 사용자 수동 실행)
- **세션 elements_json**: vibe 모드의 elements 키는 prompt와 동일(role/purpose/context/constraints/output) → 별도 마이그레이션 없이 호환

## 12. R-PCCO 루브릭과의 차이 요약

| 항목 | R-PCCO (1차) | 바이브 코딩 (4차) |
|---|---|---|
| **R 역할** | 마케터·기획자·기자 등 일반 직군 | 개발자·디자이너 (모바일 UI, 행정 UX, 게임 인터페이스 등) |
| **P 목적** | 글의 효과 (홍보·교육·전환) | 앱 사용자 행동 (클릭·검토·이탈 방지) |
| **C 맥락** | Who·Where·Why | Who·**Where(디바이스)**·When — Where 캡 규칙 |
| **C 제약** | 분량·톤·어휘·구조 | **디자인·분량·기술·금지** |
| **O 출력** | 표·리스트·대본 등 글 형식 | **파일 종류** (HTML 한 파일·React 컴포넌트 등) |
| **가점 특이사항** | 일관성·창의적 제약·자기검증 | `device_specified`·`single_file_output` 등 코딩 특화 |
| **improved_example** | 90+ 수준 개선 예시 | **Artifacts 즉시 실행 가능한 완성형 프롬프트** |

## 13. 향후 개선 아이디어 (v2)

- **Claude Code 모드 분리**: 단일 HTML(Artifacts)용 vs Claude Code(터미널)용 채점 기준 분리 — Code는 파일 구조·의존성·CLAUDE.md/README.md 짝까지 포함
- **2주차 이후 강의 연동**: 강의 회차별로 채점 기준 가중치 조정 (1주차는 5요소만, 4주차부터는 두 장 종이까지)
- **실제 Artifacts 호출 검증**: 채점기가 improved_example을 Claude API로 실제 실행해서 작동 여부 자체 검증

- **스코프 자동 분류**: 입력 묘사가 단일 HTML / React 앱 / 풀스택 등 어느 스코프인지 자동 판별 후 해당 기준으로 채점
