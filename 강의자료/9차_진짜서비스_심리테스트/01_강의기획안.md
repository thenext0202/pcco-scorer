# 9차 강의 기획안 — 진짜 서비스 만들기 (심리테스트 공유 서비스)

> **부제**: 내 컴퓨터를 꺼도 살아있는 앱 — GitHub·Vercel·Supabase 3종 세트
> **프레임워크**: 살아있는 서비스 5요소 (몸·기억·무대·창고·맥박)
> **선수강(권장)**: 6차(Claude Code)·7차(PWA 배포) — 특히 7차의 Vercel 경험 위에 쌓음
> **상태**: 기획안 v2.1 — 이론부 정식 편성 + **백엔드 키트 방식 확정** (앞단은 수강생 기획, 뒷단은 강사 제공)

---

## 0. 한 문장 요약

> **"지금까지 만든 앱은 '내 폰 안'에서만 살았다. 오늘은 코드·실행·데이터에게 각자 '집'을 줘서, 내 컴퓨터를 꺼도 살아있고 친구 폰에서도 내 데이터가 보이는 진짜 서비스를 만든다."**

수강생 각자가 Claude와 대화해서 **자기만의 심리테스트**(예: "나는 무슨 동물?", "방에 들어갔더니 이게 있다 — 뭘 고를래?")를 기획하고 → 스타터에 얹어 → GitHub(기억)·Vercel(무대)·Supabase(창고)로 배포한다. 완성되면 **결과 공유 링크**가 생겨서, 친구에게 카톡으로 보내면 친구 폰에서 내 결과가 그대로 열린다.

### v2에서 달라진 것
- 도구 3종의 **이론(왜 필요한가·무엇을 하는가·어떻게 쓰는가)**을 실습 사이에 끼워 넣지 않고, **이론부 4개 파트로 정식 편성**.
- 총 소요 약 **180분** (이론부 65 + 실습부 105 + 마무리 10). 한 번에 어렵다면 **이론부/실습부 2회 분할** 가능한 구조 (분할점 명시).

### v2.1에서 달라진 것 (스타터 방식 확정)
- 스타터가 "완성 앱 + 콘텐츠 교체"가 아니라 **백엔드 키트**로 확정 — 화면·질문 수·기능은 **수강생 각자의 기획안대로** 바이브 코딩하고, 강사는 뒷단(창고 연결 엔진 `db.js`·규칙서 `CLAUDE.md`·SQL)만 제공. **계약(인터페이스)만 고정, 구현은 자유** — 2차 I/O·8차 L의 실물 증명.
- 진행 동선 확정: 키트 폴더에서 `claude` 실행 → claude.ai에서 뽑은 기획안을 **`기획안.md` 파일로 폴더에 저장** → "기획안.md 읽고 CLAUDE.md 규칙대로 구현해줘" 한 줄로 시작. 기획안이 코드와 함께 GitHub에 커밋됨 → "기획→구현→배포의 역사가 전부 기억에 남는다."
- **웹으로 확정 (PWA 아님)**: 심리테스트는 친구가 링크로 한 번 방문하는 서비스라 설치(PWA)가 부적합 — "무엇을 만드느냐가 앱의 형태를 정한다"(7차 떡밥의 확장). 또 서비스워커 캐시가 push→자동배포 즉시 확인을 방해하므로 CLAUDE.md 규칙으로 PWA 요소 금지. PWA 개조는 심화 숙제로만.

## 1. 강의 개요

| 항목 | 내용 |
|---|---|
| 강의명 | 진짜 서비스 만들기 — 심리테스트 공유 서비스 |
| 차수 | 9차 (바이브 코딩 시리즈 · 7차의 다음 단계) |
| 소요 시간 | 약 180분 (이론 65 + 실습 105 + 마무리 10) · 2회 분할 가능 |
| 대상 | 6·7차 수강 권장. 코딩 무경험 OK |
| 배우는 도구 | **GitHub(아카이브) · Vercel(서버) · Supabase(DB)** |
| 받는 것 | **백엔드 키트**(db.js 창고 엔진 + CLAUDE.md 규칙서 + 구현요청서 + SQL + 참고샘플) + 테스트 기획용 기본 프롬프트 |
| 하는 것 | 이론(세 집의 원리) → 내 테스트 기획(Claude 대화, `기획안.md`) → 키트 위에 바이브 코딩 → GitHub push → Vercel 자동배포 → Supabase 연결 → 공유 |
| 앱 형태 | **웹**(모바일 최적화, 링크로 방문) — PWA 아님. PWA 개조는 심화 숙제 |
| 결과물 | 세상에 공개된 **내 심리테스트 URL** + 친구에게 보낸 **결과 공유 링크** |
| 채점 모드 | 없음 (랜딩만 추가) |

### 이전 강의와의 역할 분담
- **7차** = 앱을 URL로 배포했다(CLI로 한 번 던지기). **9차** = 그 배포를 **자동화된 파이프라인**(GitHub push → Vercel 자동배포)으로 업그레이드하고, 처음으로 **데이터의 집(DB)**을 갖는다.
- 4차 운세 앱(Artifacts, 못 남김) → 7차 할 일 앱(URL은 남지만 데이터는 각자 폰 안) → **9차 심리테스트(URL도 데이터도 세상에 남는다)**.
- 8차가 "설계(그림)"였다면, 9차는 그 설계가 올라가는 **기반 시설(인프라)**을 처음 직접 만져보는 날.

## 2. 시리즈 연결 (떡밥 회수 지도)

| 차수 | 만든 것 | 데이터는 어디에 | 한계 |
|---|---|---|---|
| 4차 | 운세 앱 (Artifacts) | 없음 | 브라우저 닫으면 끝 |
| 7차 | 할 일 PWA | **localStorage (내 폰 안)** | 폰 바꾸면 사라짐, 남과 공유 불가 |
| **9차** | **심리테스트 서비스** | **Supabase (창고)** | — 드디어 진짜 서비스 |

> **7차 떡밥 회수 ①**: PWA 5요소의 '저(Save)' = localStorage였다. "내 기기에만 저장"의 한계를 오늘 '창고'로 깬다.
> **7차 떡밥 회수 ②**: 7차 배포 치트시트의 "대안 — GitHub → Vercel 자동 배포"가 오늘의 메인 코스다.
> **6차 떡밥 회수**: 6차에서 GitHub는 "코드 공유하는 곳"이었다. 오늘부터는 **배포 파이프라인의 심장**이 된다.
> **2차 I/O 회수**: 테이블 스키마 = 데이터의 입출력 계약. **8차 T(Trace) 회수**: DB가 곧 서비스의 Trace.
> **1차 R-PCCO 회수**: 테스트 기획용 기본 프롬프트 자체가 R-PCCO 구조.

## 3. 프레임워크 — 살아있는 서비스 5요소 (몸·기억·무대·창고·맥박)

> 관통 질문: **"내 컴퓨터를 꺼도 서비스가 살아있으려면, 무엇이 어디에 살아야 하는가?"**

| 코드 | 요소 | 실물 | 한 줄 정의 | 비유 |
|---|---|---|---|---|
| 몸 | 앱 코드 | 내 폴더 | 내가 만든 앱 그 자체 | 몸뚱이 |
| 기억 | **GitHub** | 저장소(repo) | 코드의 역사·백업·되돌리기 | 일기장이자 금고 |
| 무대 | **Vercel** | 배포 URL | 24시간 꺼지지 않는 실행 무대 | 극장 |
| 창고 | **Supabase** | 테이블(DB) | 모두가 함께 쓰는 데이터의 집 | 은행 금고 |
| 맥박 | 자동배포 루프 | push → 재배포 | 고치면 스스로 새 버전이 되는 순환 | 심장박동 |

> **하이라이트 문장**: "코드는 GitHub에 살고, 실행은 Vercel에 살고, 데이터는 Supabase에 산다. 셋 다 내 컴퓨터가 아니다 — 그래서 내 컴퓨터를 꺼도 서비스는 산다."
> **맥박이 핵심 반전**: 셋을 이어 놓으면 이후엔 "고치고 push" 한 동작만 남는다. 서비스가 살아있다는 건 이 맥박이 뛴다는 것.

## 4. 핵심 메시지 & 킬러 인사이트

### 핵심 한 문장
> **"공유 링크가 되는 순간, 그건 앱이 아니라 서비스다."**

### 킬러 인사이트 3가지
**① 공유 링크 = DB의 존재 증명** — "내 결과 링크를 친구가 열었을 때 내 결과가 보이려면, 그 데이터는 내 폰이 아니라 **제3의 장소**에 있어야 한다." localStorage로는 논리적으로 불가능. DB가 왜 필요한지를 이론이 아니라 **카톡 한 번**으로 증명한다.

**② push가 곧 배포** — 7차에선 고칠 때마다 `vercel --prod`를 다시 쐈다. GitHub와 Vercel을 이어 놓으면 "저장하고 push"만 하면 몇십 초 뒤 전 세계에 새 버전이 뜬다. 커밋 기록 = 배포 히스토리 = 되돌릴 수 있는 기억.

**③ 세 집 분리 = 갈아끼우기 자유** — 8차 PILOT의 L(나눈다)이 서비스 규모로 커진 것. 코드·실행·데이터가 분리돼 있으니 나중에 무대를 옮기든(Vercel→다른 호스팅) 몸을 갈아엎든 창고(데이터)는 그대로다.

## 7. 이론부 상세 (Part 0~5)

### Part 0. 오프닝 — "그 앱, 지금도 살아있나요?" (8분)

- 7차 할 일 앱 소환: "URL은 살아있죠. 그런데 여러분이 적은 할 일은 어디 있죠?" → 폰 바꾸면? 친구에게 보여주려면? → **데이터가 '내 기기 안'에 산다는 것의 한계.**
- 오늘의 선언: "코드·실행·데이터에게 각자 집을 줍니다. 그러면 내 컴퓨터를 꺼도 서비스가 삽니다."
- **결과물 미리보기 (구매 유도 장면)**: 강사가 만든 완성본 심리테스트를 그 자리에서 시연 — 테스트 풀기 → 결과 → **공유 링크를 수강생 한 명에게 카톡** → 그 수강생 폰에서 강사 결과가 열림. "이게 오늘 여러분이 만드는 겁니다. 그리고 이게 '되려면' 뭐가 필요한지가 오늘의 이론입니다."

---

### Part 1. 이론 ① — 앱과 서비스는 다르다 (10분)

> 이 파트의 목표: **클라이언트·서버·클라우드**라는 단어를 수강생의 언어로 만든다. 이게 서고 나면 뒤의 세 도구는 전부 "서버의 일을 나눠 맡는 회사들"로 이해된다.

**1) 웹의 기본 구조 — 손님과 주방 (클라이언트·서버 모델)**
- 인터넷의 모든 일은 딱 두 역할: **요청하는 쪽(클라이언트)**과 **응답하는 쪽(서버)**.
- 비유: 식당. 손님(내 브라우저/폰)이 주문(요청)하면, 주방(서버)이 요리(웹페이지·데이터)를 내온다.
- 지금까지 우리 위치: 4차 Artifacts·7차 localhost는 **"내가 손님이자 주방"** — 내 기기 안에서 자급자족. 그래서 남이 못 온다.

**2) localhost의 정체**
- `localhost:3000` = "내 컴퓨터 안의 주방"이라는 뜻의 예약된 주소. 옆 사람 폰에서 열면 안 열리는 게 당연 — **주소 자체가 '각자 자기 컴퓨터'를 가리키기 때문.**
- 남들이 오게 하려면: ① 24시간 켜진 컴퓨터 ② 전 세계에서 찾아올 수 있는 주소(도메인) ③ 안전한 연결(HTTPS). 셋 다 내 노트북엔 없다.

**3) 클라우드 = 남의 컴퓨터를 빌려 쓰기**
- "그럼 24시간 컴퓨터를 사서 돌려야 하나요?" → 아니다. **이미 데이터센터에 컴퓨터를 수만 대 켜놓고 빌려주는 회사들**이 있다. 이게 클라우드의 전부다.
- 오늘 쓰는 셋도 전부 클라우드 회사다. 단, **빌려주는 게 다르다**:

| 회사 | 빌려주는 것 | 우리말 |
|---|---|---|
| GitHub | 코드 보관용 컴퓨터 | 기억 |
| Vercel | 앱 실행용 컴퓨터 + 주소 + HTTPS | 무대 |
| Supabase | 데이터 보관용 컴퓨터 + 관리 화면 | 창고 |

**4) 왜 셋으로 나누나? (한 회사가 다 하면 안 되나)**
- 8차 PILOT의 L(나눈다) 회수: **한 층 = 한 책임**. 코드·실행·데이터는 성격이 다르다 — 코드는 "역사"가 중요하고, 실행은 "안 꺼짐"이 중요하고, 데이터는 "안 잃어버림 + 규칙"이 중요하다.
- 나눠 놓으면 갈아끼울 수 있다: 무대를 Vercel에서 다른 곳으로 옮겨도 기억(GitHub)과 창고(Supabase)는 그대로.
- 참고: 실제로 우리 채점기(이 강의 플랫폼)도 똑같이 산다 — 코드는 GitHub, 무대는 Railway(Vercel의 형제 같은 회사), 창고는 Supabase. "오늘 배우는 구조가 장난감이 아니라 진짜 서비스의 표준 구조입니다."

**칠판 정리 (이 파트에서 남길 그림)**
```
[손님: 브라우저·폰]  ──요청──▶  [주방: 서버]  ──응답──▶  화면
   누구나, 어디서나              24시간 켜진 남의 컴퓨터(클라우드)
                                 └ 코드는 GitHub / 실행은 Vercel / 데이터는 Supabase
```

### Part 2. 이론 ② — GitHub, 코드의 기억 (12분)

#### 왜 필요한가 — 없으면 생기는 일
- **컴퓨터가 고장 나면 끝**: 코드가 내 폴더에만 있으면, 노트북 하나가 곧 서비스 전체다.
- **되돌릴 수 없다**: `최종.js`, `최종_진짜.js`, `최종_진짜2.js`… 6차 파일 변경기로 정리했던 바로 그 지옥이 코드에서 재현된다. "어제까진 됐는데" 상태로 못 돌아간다.
- **아무도 못 가져간다**: 이게 오늘의 핵심 — **Vercel이 내 코드를 가져갈 공식 주소가 없으면 자동배포 자체가 성립 안 된다.** GitHub는 백업집이면서 동시에 **다른 서비스들이 내 코드를 데려가는 접선 장소**다.

> 한 줄: **"GitHub는 코드의 원본 보관소이자 역사책이고, 개발 세계의 신분증이다."**

#### 배경 이론 — 버전 관리란 (5분 강의 거리)
- **버전 관리 = "지금 상태"를 이름 붙여 저장해두고, 언제든 그 시점으로 돌아가는 기술.** 게임 세이브와 완전히 같다.
- 도구 이름은 **Git**(내 컴퓨터에서 도는 세이브 프로그램), **GitHub**(그 세이브 파일들을 올려두는 클라우드). Git이 게임기라면 GitHub는 클라우드 세이브 서버.
- **커밋(commit)** = 세이브 1회. 스냅샷 + "뭘 바꿨는지" 메모가 함께 저장된다. 좋은 커밋 메모는 미래의 나에게 보내는 쪽지.
- **푸시(push)** = 내 세이브들을 GitHub에 올리기. 푸시해야 비로소 "내 컴퓨터 밖"에 존재한다.
- (한 줄만) **브랜치** = 세이브를 복제해서 딴 길로 가보는 것. 오늘은 본선(main) 하나만 쓴다.
- 왜 전 세계가 Git을 쓰나: 전 세계 개발자의 표준. 회사 입사하면 첫날 배우는 게 이것. **public repo는 그대로 포트폴리오가 된다** — "여러분 GitHub 주소가 이력서에 들어가는 시대."

#### 무엇을 하는가 — 기능 지도
| 기능 | 뭐 하는 것 | 비유 |
|---|---|---|
| **저장소(repo)** | 프로젝트 하나가 사는 방. 주소가 생긴다 (`github.com/아이디/프로젝트명`) | 프로젝트의 집 주소 |
| **커밋(commit)** | "지금 상태를 기록" — 뭘 바꿨는지 메모와 함께 저장 | 게임 세이브 포인트 |
| **푸시(push)** | 내 컴퓨터의 커밋들을 GitHub로 올리기 | 세이브 파일을 금고에 넣기 |
| **히스토리** | 모든 커밋이 시간순으로 남음. 아무 시점으로 되돌리기 가능 | 타임머신 |
| **README** | repo 첫 화면에 보이는 소개문 (4차 "사람한테 한 장" 회수) | 집 문패 |
| **공개/비공개** | public이면 누구나 코드 열람(포트폴리오!), private이면 나만 | 오픈하우스 / 자물쇠 |
| (참고) Issues·PR | 여럿이 협업할 때 쓰는 게시판·검토 절차 — 오늘은 안 씀 | 회사의 결재 라인 |

#### 어떻게 쓰는가 — 오늘 쓰는 동작은 딱 3개
수강생은 명령어를 외우지 않는다. **Claude Code에게 말로 시키고**, 무슨 일이 일어났는지만 이해한다.

| 순서 | Claude Code에게 하는 말 | 뒤에서 일어나는 일 | 확인 방법 |
|---|---|---|---|
| ① 처음 한 번 | "GitHub에 로그인해줘 (gh auth login). 브라우저 인증은 내가 할게" | 내 컴퓨터 ↔ GitHub 연결 | "Logged in" 메시지 |
| ② 처음 한 번 | "이 폴더를 GitHub 새 저장소로 올려줘. 이름은 my-test" | git init → 첫 커밋 → repo 생성 → push | 브라우저에서 repo 페이지 열어 내 파일 확인 |
| ③ 이후 반복 | "바뀐 내용 커밋하고 push해줘" | 세이브 → 금고에 올리기 | repo의 커밋 목록에 한 줄 추가 |

- **웹에서 볼 것**: repo 페이지에서 ⓐ 파일 목록 ⓑ commits 클릭 → 역사 목록 ⓒ 커밋 하나 클릭 → **빨강(지운 줄)/초록(넣은 줄)** 비교 화면. "이게 '뭘 고쳤는지'의 증거입니다."
- **오늘 규칙**: 의미 있는 변경마다 커밋 1개 (콘텐츠 교체 / 디자인 수정 / DB 연결 — 최소 3커밋이 쌓인다).
- 무료 한도: 개인 repo 무제한. 학습용으론 사실상 제한 없음.

### Part 3. 이론 ③ — Vercel, 실행의 무대 (12분)

#### 왜 필요한가 — 없으면 생기는 일
- **localhost는 나만의 세계** (Part 1 회수): 친구에게 보낼 수 없다.
- **내 컴퓨터를 서버로 쓰면**: 24시간 켜둬야 하고, 주소(도메인)도 없고, HTTPS도 없다 — 7차에서 배웠듯 HTTPS가 없으면 PWA 설치도, 공유도 반쪽이다.
- **7차와의 차이**: 7차 CLI 배포(`vercel --prod`)는 "완성본을 택배로 한 번 보내기"였다. 고칠 때마다 다시 보내야 했다. 오늘은 GitHub와 이어서 **컨베이어 벨트**를 깐다 — push하면 알아서 새 버전이 무대에 오른다.

> 한 줄: **"Vercel은 24시간 꺼지지 않는 극장이다. GitHub와 이어두면, 대본(코드)을 고칠 때마다 무대가 스스로 바뀐다."**

#### 배경 이론 — 배포와 자동배포 (5분 강의 거리)
- **호스팅** = 내 앱 파일을 남의 24시간 컴퓨터에 얹어 인터넷에 공개하는 것. **배포(deploy)** = 그 얹는 행위.
- **도메인과 HTTPS**: 배포하면 `내앱.vercel.app`이라는 전 세계 유일 주소가 생기고, 자물쇠(HTTPS — 오가는 내용의 암호화)가 자동으로 채워진다. 7차에서 "설치·오프라인은 HTTPS에서만"이었던 이유가 이 자물쇠.
- **정적 사이트 vs 동적**: 우리 앱은 파일 그대로 내보내면 되는 **정적 사이트**(주방에서 조리가 필요 없는 도시락). 그래서 배포가 이렇게 간단하다. 조리(서버 계산)가 필요한 앱은 설정이 좀 더 붙는다 — 오늘은 몰라도 됨.
- **자동배포(CI/CD)**: "코드가 바뀌면(push) → 자동으로 가져가서 → 자동으로 배포"하는 컨베이어 벨트. 현업에선 이것 없이 일 안 한다 — 사람이 손으로 배포하면 실수하고, 늦고, 무섭기 때문. 오늘 우리가 이 현업 표준을 그대로 깐다.
- **배포 기록과 롤백**: 배포도 커밋처럼 역사가 남는다. 새 버전이 망가지면 **클릭 한 번으로 직전 버전으로 복귀**(롤백). "무서워서 못 고친다"가 사라지는 이유.

#### 무엇을 하는가 — 기능 지도
| 기능 | 뭐 하는 것 | 오늘 쓰나 |
|---|---|---|
| **호스팅** | 내 앱을 인터넷에 올려 `https://내앱.vercel.app` 주소 발급 (HTTPS 자동) | ✅ |
| **GitHub 연동 자동배포** ⭐ | repo를 연결하면, push할 때마다 새 버전을 자동으로 가져가 배포 | ✅ 오늘의 핵심 |
| **Deployments(배포 기록)** | 배포 한 건 한 건이 목록으로 남음 — 어떤 커밋이 언제 무대에 올랐는지 | ✅ 관람 |
| **롤백** | 새 버전이 망가지면 클릭 한 번으로 이전 배포로 복귀 | 시연만 |
| **미리보기 배포** | 커밋/브랜치마다 임시 URL 생성 (본 무대 전 리허설) | 언급만 |
| **도메인 연결** | `내이름.com` 같은 진짜 주소 연결 가능 | 언급만 |
| **환경변수** | 비밀 값을 코드 밖에 보관하는 금고 | 언급만 (오늘 불필요한 이유는 Supabase 열쇠 이론에서) |

#### 어떻게 쓰는가 — 처음 한 번 5클릭, 이후엔 0클릭
**처음 한 번 (실습 Part 9에서):**
1. vercel.com → **Continue with GitHub**로 로그인 (계정 연동이 이 순간 끝남)
2. **Add New → Project** → 내 repo 옆 **Import** (안 보이면: GitHub 권한 창에서 해당 repo 허용)
3. 설정은 그대로 (Framework: **Other**, 정적 사이트라 빌드 설정 불필요) → **Deploy**
4. 약 1분 → 🎉 화면과 함께 `https://my-test-xxx.vercel.app` 발급 → **Visit**으로 열기
5. 그 주소를 폰에서 열어 확인 — "이제 여러분 앱은 내 컴퓨터가 아니라 무대 위에 삽니다."

**이후 (실습 Part 11, 이게 진짜):**
- 하는 일: Claude Code에 "커밋하고 push해줘" — **끝.**
- 구경할 것: Vercel 대시보드 → Deployments에 새 줄이 **Building… → Ready**로 바뀌는 것. "제가 Vercel엔 손도 안 댔죠? push가 방아쇠입니다."
- 읽는 법: 각 배포 줄에 **커밋 메시지**가 그대로 붙어 있다 → "GitHub의 기억과 Vercel의 무대가 한 줄로 이어져 있다"는 증거.
- 무료(Hobby) 한도: 개인·비상업 학습엔 충분. 상업 서비스로 키울 땐 유료 전환 — 수업 직전 vercel.com 정책 한 번 확인(7차 방침 계승).

### Part 4. 이론 ④ — Supabase, 데이터의 창고 (15분)

#### 왜 필요한가 — 없으면 생기는 일
- **localStorage의 감옥**: 7차 할 일 앱의 데이터는 '그 브라우저' 안에 산다. 폰을 바꾸면 사라지고, 친구는 절대 볼 수 없고, "전체 응답자 통계" 같은 건 원리적으로 불가능하다.
- **공유 링크의 논리**: 내 결과 링크를 친구가 열었을 때 내 결과가 보이려면, 그 데이터는 내 폰도 친구 폰도 아닌 **제3의 장소**에 있어야 한다. 그 장소가 DB다.
- **DB 서버를 직접 차리면**: 컴퓨터 한 대를 24시간 돌리며 DB 프로그램 설치·보안·백업을 직접 해야 한다 → Supabase는 이걸 통째로 빌려주고, 심지어 **엑셀처럼 눈으로 보는 관리 화면**까지 준다.

> 한 줄: **"Supabase는 모두가 함께 쓰는 은행 금고다. 넣고(insert)·꺼내고(select), 출입 규칙(RLS)은 금고가 지킨다."**

#### 배경 이론 ⓐ — 데이터베이스란 무엇인가 (5분 강의 거리)
- **"그냥 파일에 저장하면 안 되나요?"** — 세 가지가 무너진다:
  1. **동시성**: 100명이 동시에 결과를 저장하면 파일은 서로 덮어쓴다. DB는 줄 세워서 한 건도 안 잃는다.
  2. **검색**: "id가 abc123인 결과 하나만"을 파일에선 전부 읽어야 찾는다. DB는 즉시 꺼낸다.
  3. **규칙**: "이름은 비워두면 안 됨, 유형은 4개 중 하나" 같은 규칙을 DB가 지켜준다.
- **관계형 DB와 테이블**: 데이터를 **표(테이블)**로 저장하는 방식. **열(컬럼)** = 항목(이름·유형·시각), **행(row)** = 데이터 1건(응답 하나). "엑셀 시트인데, 규칙을 지키고, 동시에 만 명이 써도 안 깨지는 엑셀."
- 우리 테이블 설계 (2차 I/O 계약의 데이터판):

```
results 테이블
┌────────┬─────────┬─────────┬──────────────┬────────────┐
│ id     │ name    │ type    │ answers      │ created_at │  ← 열(항목)
├────────┼─────────┼─────────┼──────────────┼────────────┤
│ abc123 │ 김수강  │ 강아지  │ [1,3,2,4,1]  │ 7/22 19:03 │  ← 행(응답 1건)
│ xy98z7 │ 이열심  │ 고양이  │ [2,2,1,4,3]  │ 7/22 19:04 │
└────────┴─────────┴─────────┴──────────────┴────────────┘
```

- **SQL** = 창고에 말 거는 표준 언어. 동사 4개가 전부: **INSERT**(넣기)·**SELECT**(꺼내기)·UPDATE(고치기)·DELETE(지우기). 오늘 앱은 앞의 2개만 쓴다 — "심리테스트 결과는 넣고 꺼내기만 하면 되니까."
- 참고: Supabase의 속은 **PostgreSQL** — 세계에서 가장 사랑받는 오픈소스 DB. "장난감이 아니라 대기업들이 쓰는 그 엔진을 무료로 빌리는 것."

#### 배경 이론 ⓑ — 열쇠와 출입 규칙 (보안, 4분 강의 거리)
- 창고가 인터넷에 있다는 건 **아무나 문을 두드릴 수 있다**는 뜻. 그래서 열쇠와 규칙이 필요하다.
- **열쇠가 2개다 (오늘의 보안 핵심)**:
  - `anon` 키 = **손님용 방문증**. 코드에 넣어 공개돼도 된다. 이 열쇠로 뭘 할 수 있는지는 문지기(RLS)가 정한다.
  - `service_role` 키 = **마스터키**. 문지기를 무시하고 다 할 수 있다. **절대 코드·GitHub에 올리지 않는다.** 오늘은 꺼내지도 않는다.
- **RLS(Row Level Security) = 문지기의 규칙표**. 오늘 규칙: "누구나 결과를 **넣을 수** 있고(insert), 누구나 **읽을 수** 있다(select). 하지만 **고치거나 지우는 건 아무도 못 한다**." — 그래서 anon 키가 공개돼도 남의 결과를 조작할 수 없다.
- 습관 문장: **"공개돼도 되는 열쇠인지 아닌지 모르겠으면, 일단 공개하지 마라."**

#### 무엇을 하는가 — 기능 지도
| 기능 | 뭐 하는 것 | 비유 | 오늘 쓰나 |
|---|---|---|---|
| **테이블(DB)** | 데이터가 저장되는 표 | 규칙 있는 엑셀 시트 | ✅ `results` 1개 |
| **Table Editor** | 테이블 속을 눈으로 보고 만지는 화면 | 창고 유리창 | ✅ 내 응답 꽂히는 것 관람 |
| **SQL Editor** | SQL을 실행하는 곳 | 창고 설계 사무소 | ✅ 강사 SQL 복붙 1회 |
| **자동 API** ⭐ | 테이블을 만들면 "넣기/꺼내기 창구"가 자동 생성 — 코드에서 `insert`·`select` 한 줄로 사용 | 은행 창구가 저절로 생김 | ✅ Claude Code가 연결 |
| **RLS(보안 정책)** | "누가 뭘 할 수 있나" 출입 규칙 | 문지기의 규칙표 | ✅ 강사 SQL에 포함 |
| **Realtime** | 데이터가 바뀌면 화면에 즉시 반영 — **우리 채점기 리더보드가 바로 이것** | 창고 CCTV 생중계 | 언급만 (떡밥) |
| Auth(로그인)·Storage(파일) | 회원가입·이미지 저장 등 | — | 다음 기회 예고 |

#### 어떻게 쓰는가 — 창고 개설 4단계 (실습 Part 10에서 실행)
1. **프로젝트 생성**: supabase.com → New Project → 이름 아무거나, **Region: Northeast Asia (Seoul)**, DB 비밀번호는 만들어서 메모(오늘 다시 쓸 일은 없음). 생성 1~2분 대기.
2. **테이블 만들기**: 좌측 **SQL Editor** → 강사 제공 SQL 전체 붙여넣기 → **Run**. ("Success" 한 줄이면 테이블+출입 규칙까지 완성. 클릭으로 만들면 10분, SQL이면 10초.)
3. **열쇠 복사**: **Settings → API** → **Project URL**과 **anon public key** 복사. (마스터키는 건드리지 않는다.)
4. **앱과 연결**: Claude Code에게 — "config.js에 이 URL과 anon key를 넣고, 결과 저장은 results 테이블에 insert, 공유 링크로 열 땐 id로 select 하도록 db.js를 완성해줘."

- **동작 원리 한 장** (슬라이드용):
```
[결과 저장]  내 브라우저 → insert → Supabase → 고유 id 발급 → 공유 링크(?id=abc123) 생성
[링크 열기]  친구 브라우저 → 링크의 id로 select → Supabase → 내 결과 표시
[통계]      전체 행에서 유형별 개수 집계 → "당신 유형은 전체의 23%"
```

- 무료 한도: 학습용 충분. ⚠️ 단, **무료 프로젝트는 약 1주일 미사용 시 일시정지**될 수 있음(대시보드에서 Restore 클릭으로 복구) — "몇 주 뒤 내 테스트가 안 열려요"의 1순위 원인이므로 마무리 때 미리 공지.

| **RLS(보안 정책)** | 문지기의 규칙표 — "넣기·읽기 ⭕ / 고치기·지우기 ❌" | 이론 ④ |

- R-PCCO 구조. 역할(심리테스트 기획자)·목적(대화로 나만의 테스트 기획)·맥락(웹서비스로 구현 예정·백엔드 계약 존재)·제약(유형 개념 필수·공유 기능 필수·성향 축 설계·나머지 자유)·출력(**기획안.md에 넣을 마크다운 1장**)
- 수강생은 주제만 바꿔 대화 — 질문 수·스타일·기능은 대화하며 스스로 결정.

### ③ Supabase 설정 SQL
- `results` 테이블 생성 + RLS(insert·select만 허용) 한 방 스크립트. 복붙 1회로 창고 완성.

> ⭐ **키트 설계 원칙**: Next.js 같은 빌드 도구 없이 **순수 정적 + supabase-js CDN**. 이유 — ① 7차의 정적 배포 경험 그대로 재사용 ② 빌드 실패라는 최대 리스크 제거 ③ anon key는 원래 공개돼도 되는 키라(RLS가 지킴) 환경변수 없이 config.js로 단순화. 환경변수는 이론 ③에서 "이런 금고도 있다"로 언급만.

## 12. 이번 강의로 "배워가는 것" (수강생 관점)

- **인터넷이 돌아가는 원리**: 클라이언트와 서버, 클라우드가 무엇인지 — 뉴스에 나오는 그 단어들이 내 것이 된다.
- 서비스가 살아있으려면 **코드·실행·데이터가 각자 어디 살아야 하는지** 보는 눈.
- GitHub에 올리고(기억), Vercel에 잇고(무대), Supabase를 연결하는(창고) **표준 3종 세트** — 어떤 아이디어든 이 틀에 태울 수 있다.
- "고치고 push"만으로 전 세계에 새 버전이 뜨는 **맥박(자동배포)** 감각.
- 열쇠 2종과 문지기(RLS)로 배우는 **보안의 첫 감각** — 공개해도 되는 것과 절대 안 되는 것.
- 결과: 친구에게 보낼 수 있는 **내 서비스 URL**이 손에 남는다 — 그리고 창고엔 진짜 사람들의 응답이 쌓인다.
