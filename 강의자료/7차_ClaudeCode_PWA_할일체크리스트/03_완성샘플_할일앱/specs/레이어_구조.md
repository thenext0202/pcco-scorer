# 레이어 구조 — 이 앱은 4겹으로 나뉘어 있어요

> "잘 짜인 구조"란 = 파일마다 **하나의 일**만 하고, **입력 → 출력**이 분명한 것.
> 이 앱을 고칠 때 "어디를 건드릴지"가 바로 보이는 이유입니다.

## 데이터 흐름 (한눈에)
```
[사용자 입력]
   → app.js (이벤트 감지)
   → actions.js : (현재 목록, 입력) → 새 목록     ← 순수 계산 (저장·화면 안 건드림)
   → store.js   : 새 목록 저장 (localStorage)      ← 저장만
   → render.js  : 새 목록 → 화면                   ← 그리기만
```

## 4개 레이어 = 4개 파일

| 파일 | 레이어 | 입력 → 출력 | 한 일 |
|---|---|---|---|
| `store.js` | 데이터 | (없음)→목록 / 목록→(저장) | 폰에 저장/불러오기만 |
| `actions.js` | 동작 | (목록, 입력) → 새 목록 | 추가·완료·삭제 '계산'만 (순수 함수) |
| `render.js` | 화면 | 목록 → 화면 | 데이터를 화면으로 그리기만 |
| `app.js` | 연결 | 이벤트 → actions → store → render | 레이어를 잇는다 |

## 왜 이렇게 나눴나 (학습 포인트)
- **한 파일 = 한 책임** → 고칠 곳이 명확. "기능 추가는 actions부터, 모양 바꾸기는 render·css부터."
- **actions는 순수 함수** (목록 in → 목록 out) → 저장·화면과 분리돼 테스트·재사용이 쉽다. (2차 'I/O 계약', 6차 '레이어'의 실물)
- **모든 변경은 `app.js`의 `update()` 한 곳**을 거친다 → 흐름이 한눈에.
