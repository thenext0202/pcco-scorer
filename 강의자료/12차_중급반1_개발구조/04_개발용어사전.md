## 1부 — 지형: 개발 세계는 어떻게 나뉘나

### 브라우저 (Browser)
- **비유**: 식당에 온 **손님이자, 그림 그리는 화가**.
- **무엇인가**: 크롬, 사파리, 엣지 같은 프로그램. 여러분 컴퓨터·폰에서 돌아간다. 하는 일은 딱 두 가지 — ① 주소를 **요청**으로 바꿔 서버에 보내고 ② 돌아온 재료(코드)를 받아 **화면으로 그려낸다**.
- **왜 있나**: 서버가 보내주는 건 사람이 볼 수 있는 '화면'이 아니라 화면의 '설계도'다. 그 설계도를 실제 그림으로 바꿔줄 프로그램이 필요하다 — 그게 브라우저다.
- **채점기에서**: 여러분이 채점기를 쓸 때 실제로 실행되는 곳. 화면을 그리는 건 서버가 아니라 **여러분 손안의 브라우저**다.
- **헷갈리지 마세요**: "인터넷 = 크롬"이 아니다. 크롬은 인터넷을 보는 **창문**이고, 창문은 여러 회사가 만든다(크롬·사파리·엣지·웨일 — 이름만 다른 같은 직업).

### 서버 (Server)
- **비유**: 24시간 문 여는 **주방**.
- **무엇인가**: 요청을 기다렸다가 응답하는 일을 맡은 **컴퓨터(위에서 도는 프로그램)**. 여기서 중요한 것 — 서버는 신비한 특수 장비가 아니라 **그냥 컴퓨터**다. 여러분 노트북도 서버가 될 수 있다.
- **왜 있나**: 누가 언제 접속할지 모르니, **꺼지지 않고** 항상 대기하는 컴퓨터가 한 대 필요하다. 내 노트북으로 서비스를 열면 노트북을 덮는 순간 가게가 닫힌다 — 그래서 안 꺼지는 컴퓨터를 빌려서(Railway·Vercel 등) 내 앱을 올려두는 것이다.
- **채점기에서**: Railway가 빌려준 컴퓨터 위에서 채점기 서버가 24시간 돌고 있다. 새벽 3시에 접속해도 채점이 되는 이유.
- **헷갈리지 마세요**: "서버가 죽었다" = 그 컴퓨터(프로그램)가 응답을 못 하는 상태라는 뜻이지, 물리적으로 폭발한 게 아니다.

### 요청과 응답 (Request / Response)
- **비유**: **주문서와 서빙**.
- **무엇인가**: 브라우저와 서버가 대화하는 유일한 방법. 브라우저가 "이거 주세요"(요청)를 보내면, 서버가 "여기 있습니다"(응답)를 돌려준다. 항상 이 **한 왕복** 단위로 일어난다.
- **왜 있나**: 서로 멀리 떨어진 두 컴퓨터가 일하려면 정해진 대화 규칙이 필요하다. 인터넷의 모든 일 — 검색, 영상 재생, 채점 — 이 전부 이 왕복의 반복이다.
- **채점기에서**: 주소창에 채점기 주소를 치고 엔터 → 요청 한 번. 화면이 뜸 → 응답이 도착해 브라우저가 그린 것. 채점 버튼을 누름 → 또 한 번의 요청.

### ⭐ 프론트엔드 (Frontend)
- **비유**: 손님 앞에 보이는 **홀**. (레이어 4겹의 「화면」)
- **무엇인가**: **사용자의 기기(브라우저) 안에서 실행되는 모든 것.** 버튼, 글씨, 색깔, 애니메이션 — 눈에 보이고 손에 닿는 전부.
- **왜 있나**: 아무리 좋은 기능도 사람이 쓸 수 있는 '얼굴'이 없으면 쓸 수 없다. 그 얼굴을 만드는 영역 전체를 프론트엔드라고 부른다.
- **채점기에서**: 채점 입력창, 점수 카드, 리더보드 화면 — src/components의 부품 26개와 app의 페이지들.
- **헷갈리지 마세요**: **UI vs UX** — UI(User Interface)는 **생김새**(버튼 색·배치·글꼴), UX(User eXperience)는 **경험**(몇 번 눌러야 하나, 헷갈리지 않나). "버튼이 예쁘다"는 UI 칭찬, "채점하자마자 등록 버튼이 바로 보여서 편하다"는 UX 칭찬이다.
- **기억할 것**: 프론트엔드 코드는 **전부 사용자에게 보인다** (브라우저에 내려받아져 실행되므로). 그래서 비밀은 여기 못 둔다 → 백엔드가 필요한 첫 번째 이유.

### ⭐ 백엔드 (Backend)
- **비유**: 손님이 못 들어가는 **주방 안쪽**. (레이어 4겹의 「동작」)
- **무엇인가**: **서버에서 실행되는 것.** 사용자 눈에 안 보이는 곳에서 계산하고, 판단하고, 저장을 지시한다.
- **왜 있나** — 세 가지 이유를 기억하자:
  1. **비밀**: API 키, 채점 기준 같은 건 사용자 손에 들어가면 안 된다. 프론트는 전부 보이므로 비밀은 서버에만 둔다.
  2. **신뢰**: 점수 계산을 사용자 쪽(브라우저)에서 하면 조작할 수 있다. **심판은 주방에 있어야 한다.**
  3. **힘**: 무거운 계산은 좋은 컴퓨터(서버)가 하고, 사용자 폰은 결과만 받으면 된다.
- **채점기에서**: src/app/api/score — 여러분의 프롬프트를 받아 채점 기준과 함께 Claude에 보내고, 점수를 계산해 돌려주는 골목. 여러분 폰에서 채점하지 않는 이유가 위의 셋 전부다.

### ⭐ DB · 데이터베이스 (Database)
- **비유**: 껐다 켜도 남는 **창고**. (레이어 4겹의 「데이터」)
- **무엇인가**: 데이터를 **표(테이블)** 형태로 저장하는 전문 프로그램. 표의 가로 한 줄(행) = 기록 한 건, 세로 한 칸(열) = 항목. 리더보드라면: 닉네임 | 점수 | 제출 시각.
- **왜 있나** — "그냥 파일이나 엑셀에 쓰면 안 되나?"에 대한 답:
  1. **동시성**: 100명이 동시에 제출해도 안 깨진다 (파일은 두 명만 동시에 써도 꼬인다)
  2. **검색**: 수만 건 중에서 "닉네임 A의 최고점"을 즉시 찾는다
  3. **규칙**: "점수는 숫자여야 한다" 같은 규칙 위반을 창고가 막아준다
- **채점기에서**: Supabase. 중요 — **이 창고는 우리 폴더 안에 없다.** 다른 회사 서버에 살고, 우리는 열쇠와 주소(lib/supabase.ts)만 가진다. 그래서 '연결'이 필요하다.
- **예고**: 창고 속(테이블 설계, SQL)은 16차에서 통째로 다룬다.

### ⭐ API (Application Programming Interface)
- **비유**: 프로그램끼리 쓰는 **주문 창구**. (레이어 4겹의 「연결」)
- **무엇인가**: **프로그램이 프로그램에게 말을 거는 규칙.** 사람이 화면(UI)으로 앱과 대화한다면, 프로그램은 API로 대화한다. 정해진 양식으로 요청하면 정해진 형식으로 답이 온다.
- **왜 있나**: 양식이 정해져 있으면 **서로 모르는 프로그램끼리도** 협업할 수 있다. 지도 앱이 길을 아는 것, 날씨 앱이 기온을 아는 것 — 전부 남의 API를 불러 쓰는 것이다.
- **채점기에서**: 두 군데서 쓰인다. ① 브라우저 → 채점기 서버의 /api/score (우리가 만든 창구) ② 채점기 서버 → Claude API (Anthropic이 만든 창구 — 우리 서버가 손님이 되어 채점을 주문한다).
- **헷갈리지 마세요**: API는 눈에 보이는 화면이 없다 — "주소는 있는데 화면이 없는 골목".

## 2부 — 골목과 문패: 폴더 안의 파일들

### ⭐ package.json — 재료 목록
- **비유**: 이 앱의 **재료 목록** (요리 레시피의 첫 장).
- **무엇인가**: 앱의 이름·버전, **필요한 패키지 목록**, 실행 명령어(dev·build·start)가 적힌 파일. 프로젝트의 신분증이자 장보기 목록.
- **왜 있나**: "이 앱을 돌리려면 뭐가 필요한가"를 한 파일에 적어두면, 누구든(사람이든 도구든) 그 목록만 보고 **같은 환경을 재현**할 수 있다.
- **채점기에서**: 루트에 있다. Next.js·React·Supabase 클라이언트 등이 목록에 올라 있다.
- **함께 기억**: package-lock.json = 재료 **영수증**. 목록엔 "밀가루"라고만 썼어도 영수증엔 "○○제분 중력분 1kg"처럼 **정확한 버전**이 박힌다 — 팀 전원이 같은 재료를 쓰게 해준다.

### 패키지 / npm
- **비유**: 남이 만들어둔 **부품 꾸러미** / 그걸 사 오는 **가게**.
- **무엇인가**: 패키지 = 다른 개발자들이 만들어 공개한 코드 묶음(달력 위젯, 차트, DB 연결 도구…). npm = 그 패키지들이 모여 있는 세계 최대 가게(무료)이자, 사 오는 명령어.
- **왜 있나**: 모든 걸 직접 만들면 아무것도 못 만든다. 바퀴는 사 오고, 우리는 차를 조립한다.
- **채점기에서**: `npm install` 한 줄이 package.json의 목록을 보고 가게에서 전부 사 온다.

### node_modules — 창고
- **비유**: **장 봐온 창고**.
- **무엇인가**: npm이 사 온 패키지들이 실제로 저장되는 폴더. 프로젝트에서 가장 무겁다 (수만 개 파일).
- **왜 있나**: 목록(package.json)과 실물(창고)을 분리하기 위해서다. 실물은 언제든 목록으로 다시 채울 수 있으니, **GitHub에는 목록만 올리고 창고는 안 올린다**.
- **오늘의 퀴즈 정답**: node_modules를 통째로 지워도 앱은 죽지 않는다 — `npm install` 한 번이면 창고가 다시 채워진다. **재료 목록만 있으면 창고는 재생된다.**

### 빌드 (Build)
- **비유**: 재료를 **조리**해서 내놓을 상태로 만드는 것.
- **무엇인가**: 개발자가 쓰기 편한 형태의 코드(여러 파일, TypeScript, 주석…)를 **브라우저와 서버가 실행하기 좋은 형태**로 변환·압축하는 과정. `npm run build`.
- **왜 있나**: 쓰기 좋은 형태와 돌리기 좋은 형태는 다르다. 재료 손질(개발)과 서빙 접시(빌드 결과)를 분리하는 것.
- **채점기에서**: 빌드 결과는 .next 폴더에 담긴다 — 이것도 "내가 안 만든(도구가 만든)" 폴더라 GitHub에 안 올라간다.

### 배포 (Deploy)
- **비유**: 조리된 앱을 **무대에 올리는 것**. (9차 5요소의 「무대」)
- **무엇인가**: 빌드된 앱을 안 꺼지는 컴퓨터(서버)에 올려서, 세상 누구나 주소로 접속할 수 있게 만드는 일.
- **왜 있나**: 내 컴퓨터의 앱은 나만 쓸 수 있다. 남이 쓰려면 무대에 올라가야 한다.
- **채점기에서**: GitHub에 push하면 Railway가 알아서 빌드→배포한다 (9차의 「맥박」 — 자동 배포).

### ⭐ 환경변수 · .env — 열쇠 서랍
- **비유**: 코드 밖에 두는 **열쇠 서랍**.
- **무엇인가**: API 키, DB 비밀번호 같은 **비밀값**을 코드와 분리해 담아두는 파일(.env, .env.local).
- **왜 있나**: 비밀을 코드에 직접 쓰면 GitHub에 올라가는 순간 전 세계에 공개된다. 열쇠는 서랍에 따로 — 그리고 서랍은 문지기(.gitignore)가 지킨다.
- **채점기에서**: .env.local에 ANTHROPIC_API_KEY 등 3개가 산다. 이 파일은 **서버에서만 열린다** — 프론트엔드는 전부 보이니까. (왜 위험한지는 16차 보안에서.)

### .gitignore — 문지기
- **비유**: GitHub에 올라가면 안 되는 것들의 **출입 금지 명단**.
- **무엇인가**: git이 이 명단에 적힌 파일·폴더는 아예 없는 셈 치게 만드는 설정 파일.
- **왜 있나**: 세 부류를 막는다 — ① 비밀(.env — 유출 사고 방지) ② 재생 가능한 것(node_modules, .next — 목록만 있으면 되니까) ③ 각자 다른 것(개인 설정).
- **채점기에서**: 루트의 .gitignore가 정확히 위 셋을 막고 있다.

### README.md — 사람용 문패
- **비유**: 폴더 대문에 붙은 **사람용 문패**.
- **무엇인가**: "이 프로젝트가 뭐고, 어떻게 켜는지"를 사람에게 설명하는 문서. 처음 온 사람이 **제일 먼저** 읽으라고 이름도 대문자로 소리친다(READ ME!).
- **왜 있나**: 폴더만 봐서는 이게 뭔지 모른다. 6개월 뒤의 나도 '처음 온 사람'이다.
- **채점기에서**: 루트의 README.md — 프로젝트 소개와 실행 방법.

### CLAUDE.md — AI용 문패
- **비유**: **AI용 문패** — AI 직원에게 주는 업무 수칙.
- **무엇인가**: 이 프로젝트의 규칙·함정·히스토리를 **AI에게** 알려주는 문서. AI가 작업 전에 읽고 사고를 예방한다. (6차에서 우리가 직접 만들어봤다.)
- **왜 있나**: AI는 매번 처음 출근한 직원과 같다 — 수칙이 없으면 매번 같은 사고를 낸다. 문서가 곧 AI의 기억이다.
- **채점기에서**: 39KB, A4 30장 분량 — 11개 강의의 역사와 "이건 건드리지 마시오" 함정 목록까지 전부 적혀 있다.

## 3부 — 이름들: 헷갈리는 것들 정리

### 언어 vs 프레임워크 vs 라이브러리 ⭐
- **비유**: **말 / 조립 키트 / 부품 상자**.
- **언어** = 코드를 쓰는 말. JavaScript, Python. (말이 다르면 문법이 다르다)
- **라이브러리** = 필요할 때 꺼내 쓰는 부품 상자. 내가 주도권을 쥐고 부품을 골라 쓴다. 예: React.
- **프레임워크** = 뼈대까지 잡아주는 조립 키트. **폴더 구조·규칙을 키트가 정하고 나는 빈칸을 채운다.** 예: Next.js.
- **구분 요령**: 내가 부르면 라이브러리, 나를 부르면(틀이 나를 끼워 넣으면) 프레임워크.

### JS → TS → React → Next.js — 러시아 인형
- **JavaScript(JS)**: 브라우저가 알아듣는 유일한 언어 — 웹의 모국어.
- **TypeScript(TS)**: JS에 **타입(약속)을 얹은 것.** "이 값은 숫자다"라고 미리 약속해서 실수를 실행 전에 잡는다. 파일 확장자가 .ts/.tsx인 이유.
- **React**: 화면을 **부품(컴포넌트)으로 조립**하는 방식을 제공하는 라이브러리.
- **Next.js**: React로 **앱 전체**(주소, 서버, 빌드까지)를 짓게 해주는 프레임워크. "폴더가 곧 주소" 규칙도 Next.js가 정한 것.
- **한 줄 정리**: 채점기는 **Next.js로 지은 앱**이고, 그 속은 **React 부품**이고, 그 부품은 **TypeScript**로 쓰였고, TS는 결국 **JavaScript**다 — 러시아 인형.

### 컴포넌트 (Component)
- **비유**: 화면을 조립하는 **레고 부품**.
- **무엇인가**: 화면의 한 조각(버튼, 카드, 목록)을 **재사용 가능한 부품**으로 만든 것. 한 번 만들면 여러 화면에서 꺼내 쓴다.
- **왜 있나**: 같은 버튼을 열 군데 복사해두면, 수정할 때 열 군데를 고쳐야 한다. 부품이면 한 번만 고친다.
- **채점기에서**: src/components의 26개 — 채점 카드 5종, 결과 카드 5종, 공용 버튼·카드(ui/) 등. 14차의 주인공.

### 라우트 / URL (주소)
- **비유**: **폴더가 곧 주소** — app 안의 골목길이 그대로 URL이 된다.
- **무엇인가**: 라우트 = 주소와 화면(또는 창구)의 연결. Next.js에서는 app 폴더 안의 폴더 경로가 그대로 주소가 된다.
- **채점기에서**: app/practice → /practice. app/play/[code] → /play/ABCD (**대괄호 = 변하는 주소** — 세션 코드마다 다른 방). app/api/score → 화면 없는 창구.

### 타입 / 계약 (Type)
- **비유**: 주고받는 데이터의 **생김새 약속** — 2차 I/O 계약의 코드판.
- **무엇인가**: "점수는 {총점: 숫자, 축별 점수: 숫자 4개, 코멘트: 글}처럼 생겼다"를 코드로 못 박은 것.
- **왜 있나**: 약속이 없으면 점수 모양이 바뀔 때 어디가 깨질지 아무도 모른다. 약속이 있으면 어긋나는 순간 도구가 알려준다.
- **채점기에서**: src/types/score.ts(점수의 생김새), session.ts(세션의 생김새).
