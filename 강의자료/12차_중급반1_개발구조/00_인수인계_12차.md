## 3. 핵심 정의 (모든 자료에서 이 문구 그대로)

**개발 지도 3층**: 지형(프론트·백·DB·API) / 골목(폴더는 왜 갈라졌나) / 문패(파일들의 신분)

**4겹 실명 + 개념 핵심** (v2 — 각각 독립 슬라이드로 바닥부터 가르친다):
| 4겹 | 실명 | 개념 핵심 |
|---|---|---|
| 화면 | 프론트엔드 | 브라우저 안에서 실행되는 전부 · UI(생김새) vs UX(경험) · **코드가 전부 사용자에게 보인다** |
| 동작 | 백엔드 | 서버에서 실행 · 숨기는 이유 3 = **비밀·신뢰·힘** |
| 데이터 | DB | 표(테이블)로 저장하는 전문 프로그램 · 파일과 다른 3 = **동시성·검색·규칙** |
| 연결 | API | 프로그램끼리의 대화 규칙 · 양식 덕에 모르는 프로그램끼리 협업 |

**등장인물**: 브라우저 = 손님이자 화가(설계도를 받아 그린다) / 서버 = **그냥 컴퓨터**, 응답하는 일을 맡은 안 꺼지는 컴퓨터 (내 노트북도 서버가 될 수 있다 — 덮으면 가게가 닫힐 뿐)

**이름 정리(러시아 인형)**: 언어=말 / 라이브러리=내가 부르는 부품 상자 / 프레임워크=나를 끼워 넣는 조립 키트. JS(웹의 모국어)→TS(약속을 얹음)→React(부품 조립 라이브러리)→Next.js(앱 전체를 짓는 프레임워크·폴더 규칙까지 정함).

**좋은 구조의 원칙 5**: ①한 폴더=한 책임 ②화면·동작 분리(섞으면 서로 인질) ③계약은 따로(types, 2차 I/O 한 줄) ④데이터·코드 분리(content.ts 225KB — "강의 11개 동안 고친 건 대부분 이 파일 하나") ⑤문패(사람용 README·AI용 CLAUDE.md — "AI는 매번 처음 출근한 직원")

**여정 2개(수미상관)**: ①주소창(주소→요청→서버가 설계도 준비→응답·브라우저가 그림) ②채점 버튼(버튼[화면]→/api/score[연결]→채점 기준+Claude[동작·🔑서버에서만]→결과 카드[화면]→Supabase[데이터]→리더보드[화면])
