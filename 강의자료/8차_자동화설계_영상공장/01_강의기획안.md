# 8차 강의 기획안 — 자동화 설계 (실전 영상 공장 해부)

> **한 줄**: 하나의 큰 자동화를, 어떻게 **쪼개고·잇고·나누고·남기고·지키는가**.
> **방식**: 선생님이 실제로 구현한 "제품 광고 영상 자동생성 공장"을 함께 **해부**하며 설계 원리를 뽑아내고 → 각자 **'내 자동화 설계도'** 한 장을 그린다.
> **상태**: 기획안 v1 (프레임워크·커리큘럼 확정용 초안)

---

## 0. 강의 개요

| 항목 | 내용 |
|---|---|
| 강의명 | **자동화 설계 — 실전 공장을 해부하다** |
| 차수 | 8차 |
| 소요 | 약 120분 (해부 70 + 설계 실습 40 + 마무리 10) |
| 대상 | 5차(자동화 이해)를 들었거나, "자동화를 직접 설계해 보고 싶은" 수강생 |
| 권장 선수강 | **5차(BATLR 자동화 이해)** 필수급 · 2차(지침 I/O) · 6차(레이어 구조) 있으면 이해 빠름 |
| 형식 | **해부 → 설계도**. 코드 실행 없음. 순수 **설계 역량** 강의 |
| 산출물(수강생) | **'내 자동화 설계도' 1장** (설계 5원칙 템플릿을 자기 업무에 채움) |
| 채점 모드 | 없음 (랜딩 소개 + 설계 템플릿 배포) |

### 이번 강의가 이전과 다른 점
- 5차는 "자동화가 **왜** 실패하는가 / 큰 그림"이었다면, 8차는 "**어떻게 설계하는가**"의 실전편.
- 6·7차는 "작은 프로그램/앱 하나를 **만든다**"였다면, 8차는 "여러 단계·도구·사람이 얽힌 **큰 자동화를 설계한다**".
- 교보재가 장난감이 아니라 **선생님이 실제 돌리는 영상 제작 공장** — "이게 진짜 현업 자동화구나"를 체감.

## 1. 핵심 메시지 (강의 관통 문장)

> **"자동화는 코드가 아니라 설계다. 잘 쪼개고 잘 이으면, 지휘자(사람이든 AI든)는 갈아끼우면 된다."**

- 사람들은 자동화를 "코드/툴을 붙이는 일"로 오해한다. 실제 어려움은 **어떻게 쪼개고, 무엇을 주고받게 할지**를 정하는 **설계**에 있다.
- 잘 설계된 자동화는 **오늘은 Cowork(사람이 트리거)로, 내일은 Python+API(무인)로** — 같은 설계 위에서 지휘자만 바꿔 끼운다. (교보재 공장이 실제로 이 이식을 목표로 설계됨)
- 이 문장이 8차 전체의 뼈대. 5요소는 이 문장을 실현하는 5가지 설계 결정.

## 2. 프레임워크 — 자동화 설계 5원칙 · **PILOT**

영상 공장에서 그대로 뽑아낸, 어떤 자동화에도 쓰는 5가지 설계 결정.

**PILOT** — 영상 공장에서 그대로 뽑아낸, 어떤 자동화에도 쓰는 5가지 설계 결정.
"자동화를 **조종(pilot)**한다"는 뜻으로, 다섯 글자가 곧 다섯 원칙이다.

| 글자 | 원칙 | 우리말 | 한 줄 정의 | 공장에서의 실물 |
|---|---|---|---|---|
| **P** | **Pipeline** | 쪼갠다 | 큰 일을 **순서 있는 단계**로 가로로 쪼갠다 | 파이프라인 S0~S7 (접수→분석→의도→대본→키이미지→클립→검수→합본) |
| **I** | **I/O (계약)** | 정한다 | 각 단계의 **입력→출력**을 계약(양식)으로 못 박는다 | 단계 사이 결과 파일(제품요약·의도·대본…)의 정해진 양식 |
| **L** | **Layer** | 나눈다 | **지식·실행·창구**를 층으로 세로로 나눈다 | L0 지식 / L1 스펙 / L2 오케스트레이터 / L3 인터페이스 |
| **O** | **Oversight** | 지킨다 | 위험한 곳에 **사람 관문(검수)**을 둔다 | ◆대본검수·◆스토리보드검수·◆영상검수 + 최종 승인 (휴먼인더루프) |
| **T** | **Trace** | 남긴다 | **상태를 파일에 남긴다** → 멈춰도 잇고, 지휘자를 갈아끼워도 돈다 | 실행 1건 = `runs/<날짜_제품>/` 폴더에 모든 결과+미디어 |

> **가로로 쪼개고(P 단계), 세로로 나눈다(L 레이어)** — 이 두 축의 대비가 강의의 하이라이트.
> **P·L이 뼈대**, **I가 뼈를 잇는 관절**, **O가 브레이크(안전)**, **T가 피(상태)** — 그래서 멈춰도 이어지고 지휘자를 갈아끼운다.

### 이전 강의 프레임워크와의 연결 (떡밥 회수)
- **5차 BATLR**(쪼개기·에셋화·도구·연결·기록) → 8차는 그 "쪼개기·연결"을 **설계 수준으로 심화**. 에셋=L0(지식), 기록(Record)=T(Trace, `runs/`).
- **2차 I/O 계약**(포·필·범·메) → 그대로 PILOT의 **I(I/O)**. "지침의 입출력 계약"이 자동화에선 "단계의 입출력 계약".
- **6차 레이어 구조** → 그대로 PILOT의 **L(Layer)**. 파일 하나=한 책임이 시스템 규모로 커진 것.
- **1차 R-PCCO** → 각 추론 단계(분석·대본)의 프롬프트가 곧 R-PCCO.

## 3. 커리큘럼 (해부 → 설계도)

### Part 0. 오프닝 — "자동화의 진짜 어려움" (10분)
- 흔한 착각: "툴만 붙이면 자동화된다" vs 현실: 3번째 단계에서 무너진다.
- 5차 복습 1장(BATLR)으로 다리 놓기 → "오늘은 그 '연결'을 **설계도**로 그린다."
- 오늘의 목표 선언: **남의 공장을 해부해서, 내 설계도를 그린다.**

### Part 1. 공장 견학 — "제품 정보 넣으면 광고 영상이 나온다" (15분)
- 교보재 소개: 선생님의 영상 자동생성 공장. **입력(제품)→출력(음성 광고 영상)** 데모/결과물 먼저 보여주기.
- 한 장 지도: `S0→S1→…→S7` 흐름 한눈에. "이게 오늘 해부할 시체(?)입니다."
- 아직 원리 설명 안 함 — "복잡해 보이죠? 5개 칼로 해부하면 단순해집니다."

### Part 2. 해부 P · Pipeline(쪼갠다) — 가로 분해 (12분)
- 큰 일(광고영상 제작)을 왜 8단계로 쪼갰나. 한 프롬프트로 다 시키면 왜 망하나.
- 단계의 조건: **하나의 책임 + 끝이 분명(출력이 딱 떨어짐)**.
- 실습 씨앗: "여러분 업무 하나를 3~7단계로 쪼개보세요." (설계도 P칸)

### Part 3. 해부 I · I/O(정한다) — 단계를 잇는 관절 (14분)
- 단계 사이는 **결과 파일로** 주고받는다 → (원본 X) **손으로 만든 미니 예시** 한 장으로: "대본단계 ▶ 들어가는 것: 의도 / 나오는 것: 컷별 대사".
- **입력→출력 계약**이 있으면: 단계를 따로 고치고, 따로 테스트하고, 실행자를 바꿔도 됨.
- 2차 I/O(포·필·범·메) 소환: "각 단계도 결국 입출력 계약이다."
- 실습 씨앗: "쪼갠 단계마다 '무엇이 들어가고 무엇이 나오나'를 한 줄로." (설계도 I칸)

### Part 4. 해부 L · Layer(나눈다) — 세로 분리 (13분)
- **지식(L0)·스펙(L1)·지휘자(L2)·창구(L3)** 를 왜 나눴나 = WHAT/HOW/WHERE 분리.
- 하이라이트: **"가로로 쪼개고(Pipeline), 세로로 나눈다(Layer)"** 두 축 그림.
- 얇은 오케스트레이터: 지휘자는 "순서·상태·호출"만 → 그래서 **Cowork→Python 이식**이 쉽다.
- 실습 씨앗: "내 자동화에서 '지식'과 '실행'을 갈라보기." (설계도 L칸)

### 개념 상자 · API와 MCP (Part 4 끝에 살짝, 약 6분)
- **왜 여기서?** '나눈다'에서 지휘자(Claude)가 **생성 도구**(힉스필드 등)를 부르는 대목이 나온다 — 이때 "그 도구를 **어떻게 부르나**"가 바로 API·MCP.
- **한 줄 비유로 짧게** 짚고 넘어가되, 깊게 안 판다. (아래 §3.5 개념 표를 슬라이드 1~2장으로)
- 실물 연결: 우리 공장은 지금 **MCP로 도구를 꽂아** 쓴다(이미지·영상 생성 등). 나중에 무인으로 이식하면 같은 도구를 **API(REST)**로 부른다 — **일은 그대로, 부르는 방식만 바뀜**. (`02_오케스트레이터/이식_가이드.md`의 '실행자 대응표'가 산 증거)

### Part 5. 해부 O · Oversight(지킨다) — 사람 관문 (8분)
- 자동화라고 다 무인이 아니다. **위험/비용 큰 지점 앞에 검수 게이트**(대본·스토리보드·영상).
- 자동 점검(체크리스트) → 사람 승인 → 반려 루프. "어디에 브레이크를 달까"가 설계.
- 실습 씨앗: "내 자동화에서 사람이 꼭 봐야 할 관문은 어디?" (설계도 O칸)

### Part 6. 해부 T · Trace(남긴다) — 파일이 상태다 (10분)
- `runs/<실행ID>/`에 모든 게 있다 → **세션 끊겨도 이어서**, **지휘자 갈아끼워도** 동일하게 돎(멱등).
- "메모리에 숨은 상태 금지" 원칙의 이유 = 재시작·이식·디버깅.
- 마무리 다리: 이 T(Trace) 덕분에 "MCP now → API later"로 **지휘자를 갈아끼워도** 공장이 돈다.
- 실습 씨앗: "내 자동화의 '작업 폴더'는 무엇을 담아야 하나." (설계도 T칸)

### Part 7. 설계 실습 — '내 자동화 설계도' 그리기 (35분)
- 5칸 템플릿(P·I·L·O·T)에 **각자 자기 업무 자동화**를 채운다.
- 예시 주제 은행: 콘텐츠 발행, 리포트 작성, 이메일 분류·응답, 데이터 수집·정리, 고객문의 1차 응대 등.
- 강사 순회 첨삭 → 2~3명 발표 → "이걸 Cowork/Claude Code로 어떻게 태울지" 다음 스텝 언급.

### Part 8. 마무리 (10분)
- 5원칙 회수 + 핵심 문장 재확인.
- "설계가 서면, 만드는 건 6·7차에서 배운 방식으로." → 시리즈 전체 지도에서 8차의 위치.
- 예고: (선택) 이 설계도를 실제 Python+API 러너로 이식하는 심화편.

## 3.5 개념 상자 — 어려운 용어, 딱 한 줄씩 (수강생 눈높이)

> 바이브 코딩 시리즈 수강생은 개발 용어가 낯설다. 원리 설명 중 이 단어가 나오면 **비유 한 줄**로만 짚고 지나간다(깊게 X). 슬라이드 1~2장 분량.

| 용어 | 딱 한 줄 (비유) | 공장에서 |
|---|---|---|
| **API** | 프로그램끼리 쓰는 **주문 창구**. 정해진 양식으로 요청하면 정해진 형식으로 답이 온다(식당 주문서). | 미래 무인 러너가 힉스필드·Claude를 부를 방식 |
| **MCP** | AI에게 **도구를 꽂는 표준 콘센트(USB)**. 붙이면 Claude가 그 도구를 바로 쓴다. | **지금 공장이 쓰는 방식** — 이미지·영상 생성 등 도구를 MCP로 부착 |
| **API vs MCP** | API=프로그램↔프로그램 창구 / MCP=그 창구를 **AI가 알아서 쓰게** 표준화해 꽂는 것. (MCP 뒤엔 결국 API가 있음) | MCP now → API later, **일은 동일** |
| **SDK** | API를 쉽게 쓰라고 미리 싸둔 **도구상자**(라이브러리). | 이식 시 `anthropic` SDK로 Claude 호출 |
| **REST** | API의 가장 흔한 방식 — **주소(URL)에 요청**을 보내는 것. | 힉스필드 REST `POST /video` |
| **폴링(polling)** | "다 됐어?"를 **주기적으로 물어보기**. 오래 걸리는 일에 씀. | 영상 생성 잡 제출 → 완료될 때까지 확인 |
| **아티팩트(artifact)** | 단계가 남기는 **결과 서류(파일)**. 다음 단계가 그걸 받아 이어감. | `product_brief.json`·`concept_script.json`… |
| **오케스트레이터** | 단계들을 순서대로 시키는 **지휘자**(사람이든 프로그램이든). | 지금은 Cowork, 미래는 Python 러너 |
| **멱등(idempotent)** | 같은 걸 **두 번 해도 결과 같음** → 다시 눌러도 안전. | 아티팩트 있으면 건너뜀 → 재시작 안전 |

> 💡 강의 톤: "MCP는 **AI에 도구 꽂는 USB**, API는 **프로그램 주문 창구**" 딱 이 두 줄만 확실히 남기면 성공. 나머지는 '이런 말도 있구나' 수준.

## 4. 교보재 — 영상 공장을 어떻게 보여줄까

> **⭐ 대원칙: 코드 파일 원본은 학생에게 띄우지 않는다.**
> 실제 JSON·스펙·러너 코드를 화면에 그대로 열면 초심자는 벽만 느낀다. 원본은 **강사 참고용**일 뿐이고, 학생에겐 **슬라이드에 미리 단순화해 재작성한 그림/텍스트** 또는 **PT 중 그 자리에서 판서**로 보여준다.
> → 즉 아래 표의 '원본'은 **강사가 읽고 이해할 재료**, 오른쪽 '학생에게는'이 **실제 노출 형태**.

| 개념 | 강사 참고 원본(안 띄움) | 학생에게는 (이렇게 보여줌) |
|---|---|---|
| 전체 흐름 | `README.md`의 S0~S7 지도 | 슬라이드 1장 — **아이콘 8칸 화살표** 흐름도(제품→…→영상) |
| 쪼갠다(단계) | `01_파이프라인/S0~S7_*.md` | "한 프롬프트로 다 시키면 왜 망하나" **말로 풀고**, 단계 카드 8장으로 재작성 |
| 정한다(계약) | `스키마/*.schema.json` | 진짜 스키마 X → **손으로 만든 미니 예시**: `대본단계 ▶ 들어가는 것: 의도 / 나오는 것: 컷별 대사·프롬프트` 한 장 |
| 나눈다(레이어) | 각 폴더 README | **2층 빌딩 그림**(지식·스펙·지휘자·창구) 슬라이드로 재작성 |
| 지휘자·이식 | `이식_가이드.md` 대응표 | "**MCP now → API later, 일은 그대로**" 화살표 1장으로 압축 |

## 6. 이번 강의로 "배워가는 것" (수강생 관점)

- 자동화를 **툴 문제가 아니라 설계 문제**로 보는 눈.
- 큰 일을 **가로(단계)·세로(레이어)** 두 축으로 분해하는 법.
- 단계를 **파일 계약**으로 잇고, **상태를 파일에 남겨** 재시작·이식 가능하게 만드는 법.
- **어디에 사람 관문**을 둘지 판단하는 감각.
- 결과: "내 업무 하나를 자동화하려면 어디부터 손대야 하는지" 설계도가 손에 남는다.
