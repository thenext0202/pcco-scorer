# 6차 강의 — 프로그램 구조설계안

> **대상 프로그램**: 파일 이름 일괄 변경기 — **Node 로컬 프로그램**(제자리 변경)
> **연계**: `01_강의기획안.md` Part 6(레이어/I-O 계약) · 2차 I-MRKO
> **목적**: 강사 정답본(③ 샘플)과 수강생 묘사의 기준이 되는 설계 명세
> **상태**: 설계 v2 (제자리 변경 = Node fs 방식으로 전환)

---

## 0. 한눈에 — 이 프로그램은 무엇인가

> 내 컴퓨터의 **폴더를 지정**하면 → 그 안 파일들을 규칙대로 → 미리보기로 확인하고 → **제자리에서 진짜로 이름을 바꾼다**(`fs.rename`). 잘못되면 **되돌리기**.

- 로컬 Node 서버가 브라우저 UI를 띄우고, 백엔드가 실제 파일 시스템을 만진다.
- **추가 설치 0** — Node 내장 모듈(`http`, `fs`, `path`)만 사용.
- 핵심 가치는 *기능*이 아니라 **"2단계 이상이면 레이어로 쪼개 지침 MD로 넘겨받는다"**를 코드로 보여주는 것.

> ⚠️ 제자리 변경이라 **안전이 최우선**: 미리보기 필수 · 검증 · 되돌리기 · 연습 폴더에서만.

---

## 1. 기술 스택 (가장 단순하게 · 추가 설치 0)

| 영역 | 선택 | 이유 |
|---|---|---|
| 런타임 | Node.js (내장 모듈만) | Claude Code에 동봉 → 추가 설치 없음 |
| 서버 | `http` 모듈 로컬 서버 | "로컬 서버 테스트" 체험. 의존성 0 |
| 파일 변경 | `fs` (`readdir`/`rename`) | **제자리 이름 변경** |
| UI | 순수 HTML + CSS + JS | 빌드 도구 없이 구조가 보임 |
| 폴더 지정 | UI에 폴더 경로 입력(붙여넣기) | 로컬 백엔드가 그 경로를 fs로 접근 |
| 되돌리기 | 대상 폴더에 `.rename-history.json` | 직전 변경 복원 |

> 📌 왜 브라우저 단독이 아니라 Node인가: 브라우저는 보안상 내 폴더를 못 만진다. **로컬 Node 서버**가 있어야 `fs.rename`으로 제자리 변경이 된다. (이 차이 자체가 강의 포인트 — Part 3)

## 2. 3단계 레이어 구조 — 이 강의의 심장

### 전체 그림
```
 [폴더 경로 입력]
    │  folderPath
    ▼
┌──────────────┐  〈계약1〉           ┌──────────────┐  〈계약2〉          ┌──────────────┐
│ 1단계 · 수집   │ ─ 파일목록 JSON ─▶ │ 2단계 · 변환계획 │ ─ 변경계획 JSON ─▶ │ 3단계 · 출력   │
│  collect.js  │                    │ transform.js  │                    │  output.js   │
│ fs.readdir   │                    │ (+validate.js)│                    │ fs.rename    │
│ 지침:01_수집  │                    │ 지침:02_변환  │                    │ 지침:03_출력  │
└──────────────┘                    └──────────────┘                    └──────┬───────┘
                                                                                │ 제자리 변경 + 되돌리기 기록
                                                                                ▼
                                                                        [.rename-history.json]
```

### 단계별 책임 (한 단계 = 한 책임)
| 단계 | 파일 | 입력 | 출력 | 절대 안 하는 것 |
|---|---|---|---|---|
| 1 수집 | `src/collect.js` | folderPath | **파일목록 JSON** | 이름 바꾸기 ❌ |
| 2 변환계획 | `src/transform.js` | 파일목록 JSON + 규칙 | **변경계획 JSON**(old→new) | 실제 변경 ❌ |
| 2.5 검증 | `src/validate.js` | 변경계획 JSON | 충돌 표시된 변경계획 | 규칙 변경 ❌ |
| 3 출력 | `src/output.js` | 변경계획 JSON + folderPath | **제자리 rename** + 되돌리기 기록 | 규칙 계산 ❌ |

> 2차 원칙 그대로: **접점은 JSON으로 고정, 산문 금지. 한 단계는 다른 단계 일을 침범하지 않는다.**

## 3. I/O 계약 (포·필·범·메) — 단계별 지침 MD의 핵심

### 계약1 · 수집 → 변환계획 : `파일목록 JSON`
- **포**: JSON. `{ folderPath, totalCount, files[] }`
- **필**: 각 파일 = `originalName, baseName, ext, index`
- **범**: 한 번에 최대 500개(초과 경고). 폴더 안 *파일만*(하위 폴더 제외)
- **메**: `totalCount`, `sortBy`(이름순 기본)

```json
{
  "folderPath": "C:/Users/me/Desktop/연습폴더",
  "totalCount": 3,
  "sortBy": "name",
  "files": [
    { "originalName": "IMG_3920.JPG", "baseName": "IMG_3920", "ext": ".JPG", "index": 1 },
    { "originalName": "내 사진 (1).png", "baseName": "내 사진 (1)", "ext": ".png", "index": 2 },
    { "originalName": "스크린샷.jpeg", "baseName": "스크린샷", "ext": ".jpeg", "index": 3 }
  ]
}
```

### 계약2 · 변환계획 → 출력 : `변경계획 JSON`
- **포**: JSON. `{ rule, conflictCount, plan[] }`
- **필**: 각 항목 = `originalName, newName, conflict`
- **범**: 입력 파일과 1:1. 누락·중복 금지
- **메**: `rule`(규칙 설명), `conflictCount`

```json
{
  "rule": "여행2026_ + 순번 4자리",
  "conflictCount": 0,
  "plan": [
    { "originalName": "IMG_3920.JPG", "newName": "여행2026_0001.JPG", "conflict": false },
    { "originalName": "내 사진 (1).png", "newName": "여행2026_0002.png", "conflict": false },
    { "originalName": "스크린샷.jpeg", "newName": "여행2026_0003.jpeg", "conflict": false }
  ]
}
```

### (되돌리기) 출력 단계가 남기는 기록 : `.rename-history.json`
```json
{
  "appliedAt": "2026-06-02T10:30:00+09:00",
  "folderPath": "C:/Users/me/Desktop/연습폴더",
  "changes": [
    { "from": "IMG_3920.JPG", "to": "여행2026_0001.JPG" }
  ]
}
```
> 되돌리기 = `to → from`으로 역방향 rename.

> 💡 강의 포인트: 두 지침 MD에 **같은 포맷**을 명시해야 접점이 안 깨진다(2차 "실수 ① 포맷 안 맞추기").

## 4. 기능 명세 — 변환 규칙 (2단계가 처리)

| 규칙 | 설명 | 예시 |
|---|---|---|
| 접두사 | 앞에 글자 붙이기 | `IMG.jpg` → `여행_IMG.jpg` |
| 접미사 | 확장자 앞에 붙이기 | `IMG.jpg` → `IMG_백업.jpg` |
| 순번 매기기 | 일련번호(자릿수 지정) | `여행_0001.jpg ...` |
| 찾기·바꾸기 | 이름 속 글자 치환 | `IMG_` → `사진_` |
| 공백 처리 | 공백 → `_` 또는 제거 | `내 사진.png` → `내_사진.png` |
| 대소문자 | 확장자/이름 소문자화 | `.JPG` → `.jpg` |

> 규칙 조합 가능(접두사+순번 등). 확장자는 기본 보존, "대소문자" 규칙일 때만 변경.

## 5. 안전장치 (제자리 변경 = 최우선) ⭐

1. **미리보기 필수**: 변경계획을 *표*로 먼저 보여주고(원래 → 새 이름, 충돌은 빨강), 사용자가 "적용"을 눌러야 `fs.rename` 실행.
2. **검증(2.5)**: 빈 이름·중복 새 이름·기존 파일과 충돌 자동 표시 → 충돌 있으면 적용 차단.
3. **되돌리기**: 적용 시 `.rename-history.json` 기록 → "되돌리기" 버튼으로 직전 변경 복원.
4. **연습 폴더 한정 권장**: 시스템 폴더(`C:\Windows` 등)·홈 루트 같은 위험 경로는 거부. 실습은 더미 폴더에서만.
5. **하위 폴더 미포함**: 지정 폴더 *바로 아래 파일만* 대상(재귀 변경 안 함 → 사고 방지).
6. **한글 안전**: 파일명 UTF-8 유지.

## 6. 파일·폴더 구조

```
파일이름변경기/
├── server.js               # Node 로컬 서버 (http) — UI 서빙 + API
├── src/
│   ├── collect.js          # 1단계 수집  : folderPath → 파일목록 JSON (fs.readdir)
│   ├── transform.js        # 2단계 변환  : 파일목록+규칙 → 변경계획 JSON
│   ├── validate.js         # 2.5 검증    : 충돌·빈이름
│   └── output.js           # 3단계 출력  : 변경계획 → fs.rename + 되돌리기 기록
├── public/
│   ├── index.html          # UI (폴더경로·규칙선택·미리보기표·적용/되돌리기)
│   ├── styles.css
│   └── app.js              # 화면 ↔ 서버 API 호출
├── specs/                  # ⭐ 단계별 지침 MD (I/O 계약)
│   ├── 01_수집.md
│   ├── 02_변환.md
│   └── 03_출력.md
├── package.json            # "start": "node server.js"
├── README.md               # 사람용 설명서 (남이 받아서 실행하는 법)
├── CLAUDE.md               # AI용 프로젝트 지침
└── .gitignore              # .rename-history.json, node_modules 등
```

> Artifacts(4차)는 이 전체를 단일 파일로 욱여넣어야 했다. Claude Code는 **역할별로 파일을 나눠** 레이어가 눈에 보인다 — 멀티파일의 가치.

## 7. 데이터 흐름 (런타임)

```
브라우저 UI에서 폴더경로 입력 + 규칙 선택
  → app.js: POST /api/scan { folderPath }
      server → collect.js → 파일목록 JSON              (계약1)
  → app.js: POST /api/plan { files, rule }
      server → transform.js → validate.js → 변경계획 JSON  (계약2)
  → 화면: 변경계획을 미리보기 표로 렌더 (충돌 빨강)
  → (사용자 '적용' 클릭)
  → app.js: POST /api/apply { plan, folderPath }
      server → output.js → fs.rename 제자리 변경 + .rename-history.json 기록
  → (필요시 '되돌리기' 클릭) → POST /api/undo → 역방향 rename
```

각 화살표가 **접점**이고, 넘어가는 건 항상 **구조화된 JSON**이다.

### 서버 API 요약
| 메서드/경로 | 입력 | 출력 | 담당 모듈 |
|---|---|---|---|
| `POST /api/scan` | `{ folderPath }` | 파일목록 JSON | collect |
| `POST /api/plan` | `{ files, rule }` | 변경계획 JSON | transform+validate |
| `POST /api/apply` | `{ folderPath, plan }` | 결과 + 기록 | output |
| `POST /api/undo` | `{ folderPath }` | 복원 결과 | output |

## 8. R-PCCO 묘사 프롬프트 (강의용)

### 8-1. 단순 1단계 버전 (Part 2 — "작게 시작")
```
[역할] 너는 간단한 Node 프로그램을 만드는 개발자야.
[목적] 내가 폴더 경로를 입력하면, 그 폴더 안 파일들 이름 앞에 글자를 붙여
       제자리에서 바꿔주는 가장 단순한 로컬 웹 도구를 만들고 싶어.
[맥락] Windows, Node 내장 기능만(추가 설치 없이). 로컬 서버로 띄워 브라우저에서 쓸 거야.
       파일을 실제로 바꾸기 전에 반드시 미리보기를 보여줘.
[제약] 한 파일로 단순하게 시작. 지정한 폴더 '바로 아래 파일'만. 한글 파일명 안전하게.
       실수 방지를 위해 적용 전엔 절대 안 바꾸기.
[출력] node server.js로 띄우면 브라우저에서 열리는 한 페이지. 실행 방법도 알려줘.
```

### 8-2. 레이어 재설계 버전 (Part 6 — "2단계 이상이면 쪼갠다")
```
[역할] 너는 파이프라인 구조로 코드를 깔끔히 나누는 개발자야.
[목적] 지금 엉킨 로직을 '수집 → 변환계획 → 출력' 3단계 레이어로 나누고 싶어.
[맥락] 2차 강의의 'I/O 계약'을 적용한다. 단계 사이는 JSON으로만 넘기고, 단계마다 지침 MD를 둔다.
[제약]
  - 각 단계를 src/collect.js, transform.js, output.js로 분리. 검증은 validate.js.
  - 단계별 지침을 specs/01_수집.md, 02_변환.md, 03_출력.md에 먼저 작성.
    각 지침엔 I/O 계약을 포(JSON 포맷)·필(필수 필드)·범(개수/범위)·메(메타) 4요소로 명시.
  - 한 단계는 다른 단계 일을 침범하지 않는다(한 책임). 접점은 산문 금지, JSON 고정.
  - 출력 단계는 fs.rename으로 제자리 변경하고 .rename-history.json에 되돌리기 기록을 남긴다.
[출력] specs/의 지침 MD 3개를 먼저 보여주고, 그 계약대로 각 모듈을 구현해줘.
```

> 운영: 8-2는 "지침 MD 먼저 → 그 계약대로 구현"의 **스펙 우선(spec-first)** 순서를 강조한다.

## 9. 단계별 지침 MD 견본 (specs/02_변환.md 예시)

```markdown
# 02 · 변환계획 단계 지침

## 역할
파일목록을 받아, 사용자가 고른 규칙대로 '새 이름'을 계산한다.

## 입력 (이전 단계에서 받음)
- 계약1 '파일목록 JSON' (files[]: originalName, baseName, ext, index)
- 사용자 규칙 (prefix / suffix / numbering / find-replace / space / case)

## 출력 (다음 단계로 넘김) — I/O 계약
- 포(Format): JSON. { rule, conflictCount, plan[] }
- 필(Required): plan[] 각 항목 = originalName, newName, conflict
- 범(Scope): 입력 파일과 1:1. 누락/중복 금지
- 메(Metadata): rule(규칙 설명 문자열), conflictCount(정수)

## 규칙 (이 단계만의 책임)
- 확장자는 기본 보존. '대소문자' 규칙일 때만 변경.
- 순번은 index 기준, 자릿수 패딩.
- 같은 새 이름이 둘 이상이면 conflict=true.

## 절대 하지 않는 것
- 실제 파일 변경/저장 ❌ (그건 3단계 출력의 책임)
- 파일 읽기/수집 ❌ (그건 1단계 수집의 책임)
```

> `01_수집.md`·`03_출력.md`도 같은 틀(역할·입력·출력 계약·책임·금지)로 작성 → ③ 샘플에 3개 모두 포함.

## 10. 로컬 실행 & 공유

### 로컬 서버 테스트 (Part 3)
```bash
node server.js     # → http://localhost:3000  (브라우저에서 열기)
```

### 공유하기 (Part 9) — ⭐ 솔직한 배포 수업
> **이 종류(내 파일을 만지는 도구)는 URL 배포로 남이 못 쓴다.** 배포된 웹서버는 방문자 컴퓨터의 파일을 만질 수 없기 때문(브라우저 보안). 그래서:
- **GitHub에 코드 공유** → 남이 받아서(`git clone`) **자기 컴퓨터에서 `node server.js`** 실행.
- 이게 "URL로 쓰는 서비스"와 "받아서 돌리는 도구"의 차이 — **무엇을 만드느냐에 따라 배포 방식이 다르다**는 좋은 교훈.
- (대조군 언급: 4차 운세 앱처럼 *남의 파일을 안 만지는* 웹앱은 Vercel URL 배포가 맞다.)
