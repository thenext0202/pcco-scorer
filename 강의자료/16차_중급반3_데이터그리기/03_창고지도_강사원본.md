# 03 창고 지도 — 강사 원본 (배포 금지)

> 16차 「데이터를 그린다」 강사 전용. 2026-09-14 `docs/supabase_schema.sql` · `src/lib/sessionApi.ts` · `src/lib/env.ts` · `src/lib/rateLimit.ts` 실측. 슬라이드에 올린 숫자·문구의 근거와 퀴즈 정답, 질의응답 FAQ.
> **투영 금지** — 이 문서도, Supabase 대시보드도, SQL 편집기도 띄우지 않는다. 슬라이드의 표 목업과 부록 25로만 답한다.

---

## 1. 표 목록 — 2개 (줄 1개)

채점기 창고(Supabase = PostgreSQL)에는 표가 **딱 두 장**이다. 슬라이드 숫자 셋 = **표 2 · 열 15(7+8) · 열쇠 2**.

| # | 표 | 실명 | 한 종류의 사실 | 한 줄(행) = |
|---|---|---|---|---|
| 1 | 세션 표 | `sessions` | 강사가 만든 채점 세션 | "누가, 언제, 무슨 모드로, 무슨 제목의 세션을 열었다" |
| 2 | 제출 표 | `submissions` | 참가자가 등록한 점수 | "누가(닉네임), 어느 세션에, 몇 점을, 언제 냈다" |

**줄 1개**: 제출 표의 「세션번호」(`session_id`) → 세션 표의 「번호」(`id`). 세션을 지우면 그 세션의 제출도 같이 사라진다(`ON DELETE CASCADE` — 슬라이드에선 "삭제 연쇄").

리더보드는 표가 **아니다** — 제출 표를 읽어 앱이 그린 것(슬라이드 13). 리더보드 표를 따로 만들지 않은 이유가 원칙 ⑤("판단은 읽을 때")의 증거.

## 3. 규칙 목록 (슬라이드 09·11)

| 규칙 | 우리말 | 어디에 | 창고가 막는 것 | 앱이 하는 것 |
|---|---|---|---|---|
| UNIQUE | 유일 | 세션.코드 | 같은 코드 두 줄 | 거절당하면 새 코드로 3번까지 재시도 |
| CHECK | 허용목록 | 세션.모드 | 5종 밖의 값 | — (드롭다운으로 5종만 보여줌) |
| NOT NULL | 필수 | 코드·제목·닉네임·프롬프트·총점·등급·요소점수·세션번호 | 빈 값 | 입력칸에 "필수" 표시 |
| DEFAULT | 기본값 | 번호·만든시각·만료시각·모드 | — | 안 적어도 창고가 채움 |
| REFERENCES + CASCADE | 줄 잇기 + 삭제 연쇄 | 제출.세션번호 → 세션.번호 | 없는 세션에 제출 | 세션 지우면 제출도 사라짐 |

**"앱이 아니라 창고가 막는 이유"(09)**: 앱은 여럿이 될 수 있다(폰 화면·PC 화면·나중에 만들 관리자 화면·봇). 창고는 하나. 규칙이 앱에만 있으면 새 앱이 뚫는다. → 원칙 ③.

**색인 3개(슬라이드 14)**: 코드(`idx_sessions_code`) · 세션번호+총점 내림차순(`idx_submissions_session_score`) · 모드(`idx_sessions_mode`). 비유 = 책 뒤 색인. "설계지에 안 적어도 된다 — 나중에 붙이는 것".

## 4. 읽기·쓰기 실측 (슬라이드 12·13)

채점기가 창고에 하는 일은 **둘뿐** — 만들기(INSERT)·읽기(SELECT). 고치기(UPDATE)·지우기(DELETE)는 코드에 **한 줄도 없고**, 문지기도 안 열어준다.

| 순간 | 하는 일 | 우리말 번역 (슬라이드 13용) | 실명 |
|---|---|---|---|
| 강사가 세션 만들기 | 만들기 | "세션 표에 줄 하나 — 코드·제목·호스트·모드" | `insert` |
| 참가자가 코드 입력 | 읽기 | "세션 표에서 이 코드인 줄 하나 줘" (+만료 여부는 앱이 판단) | `select … eq(code) … single` |
| 등록 버튼 | 만들기 | "제출 표에 줄 하나 — 세션번호·닉네임·프롬프트·총점·등급·요소점수" | `insert` |
| 리더보드 | 읽기 | **"제출 표에서 · 이 세션 것만 · 시간순으로 · 전부 줘"** | `select * … eq(session_id) … order(created_at)` |

**퀴즈 ② 정답(슬라이드 13)**: 재제출하면 줄이 **늘어난다**(insert 누적, 11차부터 재제출 허용). 리더보드는 전부 읽어 **닉네임별 최고점 1줄**을 앱이 골라내고, 제출 횟수(attempts)와 첫 제출 대비 상승폭(improvement — "오늘의 성장왕")을 계산한다. 동점이면 먼저 낸 사람이 위. → "창고는 사실을 남기고, 판단은 읽을 때 한다"(원칙 ⑤). 덮어썼다면 성장왕은 불가능했다.

## 5. 열쇠 2개와 문지기 (슬라이드 15·16) ⭐

| | 비밀 열쇠 | 공개 열쇠 |
|---|---|---|
| 실명 | `ANTHROPIC_API_KEY` | `NEXT_PUBLIC_SUPABASE_ANON_KEY` (+ 주소 `NEXT_PUBLIC_SUPABASE_URL`) |
| 여는 것 | Claude(채점 AI) | 창고(Supabase) |
| 어디에 | **서버 서랍(.env)에만** — `env.ts`가 서버에서만 검사 | 브라우저에 실려 나감 — `NEXT_PUBLIC_` 접두사 = "공개해도 되는 값"이라는 표시 |
| 새면 | 전원이 내 카드로 채점 — 쓰면 돈이 나감 | 문지기가 지키므로 읽기·쓰기만 가능 |
| 12차 연결 | "열쇠는 3번 스텝(서버)에서만 열립니다 — 원리는 16차에서" | "우리가 가진 건 열쇠와 주소뿐" |

**문지기(RLS) 실측 — 표마다 네 가지 허락**:
| 표 | 읽기 | 쓰기(만들기) | 고치기 | 지우기 |
|---|---|---|---|---|
| 세션 | O (모두) | O (모두) | **X** | **X** |
| 제출 | O (모두) | O (모두) | **X** | **X** |

정책 이름: `sessions_select_policy`·`sessions_insert_policy`·`submissions_select_policy`·`submissions_insert_policy` — update·delete 정책은 **없다** = RLS가 켜진 표에서 정책이 없으면 **거절**. 그래서 공개 열쇠를 가진 누구도 점수를 못 고친다.

**퀴즈 ③ 정답(슬라이드 16)**: "내 92점을 100점으로 고칠 수 있나?" → **없다.** 공개 열쇠로 고치기를 시도하면 문지기가 거절. (솔직한 부연: 새 줄을 100점으로 **추가**하는 건 막지 않는다 — 쓰기가 열려 있으니까. 그건 "채점 결과 없이 쓰기"를 막는 다음 단계 보안이고 오늘 범위 밖. 질문 나오면 "그건 다음 시즌 — 오늘은 고치기·지우기가 막혀 있다는 것까지".)

**"문지기가 없으면?"** — 공개 열쇠가 브라우저에 있으니 누구나 `delete`를 보낼 수 있다 = 창고 열쇠를 길에 떨어뜨린 것. RLS를 켜는 순간 정책이 없는 동작은 전부 거절 → "문지기는 기본이 거절".

## 6. 데이터가 사는 세 곳 실측 (슬라이드 04)

| 곳 | 실물 | 얼마나 남나 | 증거 |
|---|---|---|---|
| 주머니 (브라우저 저장) | `localStorage` — 채점기 5종 모두 쓰다 만 프롬프트를 저장(`STORAGE_KEY`), 설치 안내 "닫음"·방문 횟수 | 내 브라우저에만, 지우면 끝, 다른 기기엔 없음 | 새로고침해도 프롬프트가 남아 있는 이유 |
| 손 (서버 메모리) | `rateLimit.ts` — 인메모리 Map, **IP당 1분 10회** | 서버가 켜져 있는 동안만, 재시작하면 0 | 코드 주석: "프로덕션에선 Redis 등으로 교체 필요" — 손은 창고가 아니다 |
| 창고 (DB) | Supabase 표 2 | 앱을 꺼도·서버 재시작해도·모두에게 | 리더보드 |

"남아야 하는 것만 창고에" — 채점 결과 카드 자체는 **창고에 없다**(등록을 안 누르면 사라진다). 흐르는 것 예시로 최적.

## 7. 만료·실시간 (슬라이드 17)

- 만료: 세션 표 「만료 시각」 기본값 = 만들 때+24시간. 만료 판정은 **앱이 읽을 때** (`isExpired = expires_at < now`) — 창고가 지우는 게 아니다(원칙 ⑤와 일관: 지우지 않고 남긴다). 만료된 세션에 접속하면 "만료" 안내.
- 실시간: `ALTER PUBLICATION supabase_realtime ADD TABLE submissions` — 제출 표에 줄이 생기면 창고가 보고 있는 화면에 **알려준다**. 리더보드가 새로고침 없이 바뀌는 이유. 12차 여정 6번 스텝 "리더보드는 창고를 읽어 그린다"의 한 줄 보강.

## 8. 여정 ③ 6스텝 — 창고 눈 (슬라이드 18)

| 스텝 | 12차(지형) | 14차(화면) | **16차(창고)** |
|---|---|---|---|
| 1 버튼 | 화면 | 움직임 | 창고와 무관 — 아직 아무것도 안 남음 |
| 2 기다림 | 연결 | 상태 | 손(서버 메모리)이 "1분 10회" 세는 순간 |
| 3 서버가 채점 | 동작(🔑) | (서버) | **비밀 열쇠**로 Claude 호출 — 창고엔 안 남음 |
| 4 결과 카드 | 화면 | 부품 | **흐르는 것** — 등록 안 하면 사라진다 |
| 5 등록 | 데이터 | 부품(등록 카드) | **공개 열쇠 + 문지기 → 제출 표에 줄 하나** (오늘 유일하게 창고에 남는 순간) |
| 6 리더보드 | 화면 | 이동 | 읽기(색인 사용) + 실시간 알림 |

클로징 문장: "12차엔 지형으로, 14차엔 화면으로, 오늘은 창고로 — 같은 3초를 세 번 봤습니다. 3종 세트 완성."

## 9. 슬라이드 07 「정체 공개」 원본 (표 만드는 문장 — 우리말 주석)

실제 SQL(슬라이드엔 7줄로 압축, 타입 이름은 입 밖에 내지 않음):
```sql
CREATE TABLE submissions (
  id UUID PRIMARY KEY DEFAULT gen_random_uuid(),           -- 번호 · 창고가 붙임
  session_id UUID NOT NULL REFERENCES sessions(id),         -- 세션번호 · 세션 표를 가리킴 (줄)
  nickname VARCHAR(30) NOT NULL,                            -- 닉네임 · 글자 30자 · 필수
  prompt TEXT NOT NULL,                                     -- 프롬프트 · 긴 글 · 필수
  total_score INT NOT NULL,                                 -- 총점 · 숫자 · 필수
  grade VARCHAR(2) NOT NULL,                                -- 등급 · 글자 2자 · 필수
  elements_json JSONB NOT NULL,                             -- 요소 점수 · 덩어리 · 필수
  created_at TIMESTAMPTZ DEFAULT now()                      -- 제출 시각 · 안 적으면 지금
);
```
슬라이드에는 열 8줄 + 첫 줄("표 만들기 — 제출 표") = 9줄 중 **열 8줄만 세게** 한다. "왼쪽 표의 열 여덟 = 오른쪽 여덟 줄".

## 10. 질의응답 FAQ (예비 슬라이드 24 + 이 문서로만 답한다)

| 질문 | 답 |
|---|---|
| "SQL은 언제 배우나요?" | 다음 시즌. 오늘 4단의 눈이 없으면 SQL은 소음. 용어사전에 실명 있음 |
| "엑셀로 하면 안 되나요?" | 작은 앱은 된다(구글 시트를 창고로 쓰는 앱도 있다). 다르게 되는 건 셋 — 종류 고정·규칙·동시 사용. 여럿이 동시에 쓰기 시작하면 표가 깨진다 |
| "점수를 새 줄로 100점 넣으면요?" | 쓰기가 열려 있으니 막지 못한다 — 그건 "채점 없이 쓰기"를 막는 다음 단계(서버에서만 쓰게 하기). 오늘은 고치기·지우기까지 |
| "24시간 지나면 지워지나요?" | 아니다 — 남는다. 앱이 읽을 때 "만료"라고 판단할 뿐. 원칙 ⑤ |
| "우리 회사 데이터도 이렇게 생겼나요?" | 표·열·규칙·열쇠는 어디나 같다. 크기만 다르다 — 표 2장이 200장이 될 뿐 |
| "Supabase가 뭐예요?" | 창고를 빌려주는 회사(9차에서 만든 그것). 창고 자체는 PostgreSQL이라는 40년 된 창고 프로그램 |
| "JSON 덩어리는 왜 열로 안 쪼갰나요?" | 모드마다 요소 이름이 다르다(5요소/SSDHR/4축). 열로 쪼개면 모드 늘 때마다 표를 고쳐야 한다 — 덩어리는 "모양이 바뀌는 것"을 담는 칸. 대신 덩어리 안은 규칙이 안 지켜준다(맞바꿈) |
| "왜 리더보드 표는 없나요?" | 제출 표에서 읽을 때 계산한다. 표를 하나 더 만들면 두 표를 맞춰야 한다(같은 사실 두 곳 = 원칙 ① 위반) |
